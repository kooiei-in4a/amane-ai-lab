検討に至った背景

#検討に至った背景

この記事の調査は、最初から「未来予測レポートを書こう」として始まったものではない。
ある種の ADR統制型・AI-PR駆動・役割分離型マルチエージェント開発 を運用するなかで、「数年後の開発」と「エンジニアとしての立ち位置」を考える対話から生まれた。

以下は、その対話の流れを一般化したものである。

#1. いまの開発手法を何と呼ぶか

問い： 重要な設計判断を ADR で統制し、Issue から Draft PR・独立レビュー・検証・マージまでを AI が役割分担して進めるやり方は、「ADR開発 ＋ AI-PR駆動 ＋ マルチエージェント」と言えるか。

整理した結果：

ADR統制型の AI-PR駆動・マルチエージェント開発

要素 実態に近い言い方 要点
ADR ADR統制型（ADR駆動ではない） 重要判断の正本は ADR。ただしすべての変更が ADR 起点ではない。Issue・計画・PR も正本になりうる
AI-PR AI-PR駆動 Issue → 計画 → 実装 → Draft PR → 独立レビュー → CI → Human 承認、という状態遷移が中心
マルチエージェント 役割分離型 実装側と独立レビュー側などを分け、同じAIの反復利用とは区別する

一文にするなら次のとおり。

重要な設計判断を ADR で統制し、Issue から Draft PR・独立レビュー・検証・マージまでを AI エージェントが役割分担して進める、Human-in-the-loop 型の AI-PR駆動マルチエージェント開発。

最も外してはいけない点は、完全自律ではなく、人間が仕様決定・権限開放・最終受入を担うことである。

#2. 上手くいく点と重さ

問い： この手法は上手くいくか。

評価の骨子：

  • 品質・事故防止： 工程で暴走を抑えられるなら、かなり有効
  • 速度・運用コスト： 強度を上げすぎると重くなる

有効になりやすい理由の中心は、「AIが大量に書く」ことではなく、暴走を工程で抑えられることにある。

  • 承認済み判断がなければ勝手に補完せず停止する
  • Issue の到達点を超える実装を禁止する
  • 実装者と独立レビュアーを分ける
  • Draft / Ready / merge / cleanup で権限を段階開放する
  • 判断不足で実装を止めるケースが実際に起きうる

一方の懸念は次の2点。

  1. 重さ — 小さな変更にも同じ強度をかけすぎると、書く時間より引き継ぎ・承認の時間が勝つ
  2. レビュー重複 — 同じ観点の多重レビューは安心感は増えても発見率が頭打ちになりやすい

総合すると次のように言える。

品質モデルとしては有効になりやすい。ただし「高品質な実験運用」から「持続可能な標準運用」へ移るには、リスクに応じた軽量化が必要。

改善の方向としては、変更を Low / Medium / High / Critical に分けて工程を選択すること、およびプロセス自体の計測（Lead time、有効指摘数、再指摘率など）が挙げられる。

#3. 「数年後、確認以外は全部AI」は来るか

問い： 数年後、人間の確認・レビュー以外は AI エージェントが自動協働してシステムを構築する未来はあるか。忖度なく。

結論の骨子：

  • その未来はかなり高い確率で来る（限定領域なら 2028〜2030 年ごろでも不思議ではない）
  • ただし姿は「AI同士が自由に会議する」ではない
  • より現実的なのは、中央オーケストレーターが専門エージェントを隔離環境で動かし、機械判定可能なゲートで PR を統合する工場型

すでに「コードは人間が書かない」事例は出ている。残る課題は「人間がエージェントを逐次操作しなくてもよいか」である。

同時に、マルチエージェントは過大評価されやすい。順序依存の強い仕事では性能が悪化しうる、という研究もある。主流はおそらく次である。

強力な単一オーケストレーター ＋ 必要な箇所だけ専門エージェントへ委任

そして最大の壁は生成能力ではなく、

意図どおり実装したことをどう証明するか（検証）

へ移っている、という整理になった。

人間が「確認だけ」になる条件として、正本の明確さ、機械判定可能な受入、権限分離、証拠検証、失敗時の復旧、が挙げられる。

いま多くの現場で行われている強い Human-in-the-loop 運用は、未来方式の手動プロトタイプに近い。次の段階はモデルを賢くすることより、人間が手でやっている工程制御を仕様化して自動化することである、という診断でこの段は閉じた。

#4. 人間から見える未来像の確認

問い： Product Agent がヒアリング〜要件定義〜プレゼンし、承認後に Architecture / Planning / Implementation… が進み、人間は PM エージェントに進捗を聞き、よいタイミングでレビュー依頼を受ける——この未来像で合っているか。

答え： ほぼ合っている。修正点は1つ。

PM エージェントがすべてを頭の中で管理するのではなく、永続的なワークフロー基盤が状態を持ち、PM エージェントは人間との窓口になる

人間へのレビュー依頼は「毎週」ではなく、製品判断・ADR・リスク閾値・計画差分・マイルストーン受入・本番操作などのイベント条件で発火する、という像に精緻化できる。

人間に残る仕事は、主に次である。

  1. 何を作るか
  2. トレードオフを決める
  3. 言語化されていない要求を評価する
  4. 責任を引き受ける

#5. だから調査プロンプトが必要になった

ここまでの整理で見えてきたのは、「開発手法の延長に、検証と責任が中心の未来がある」という感触だった。

そこで知りたくなったのは次である。

  • ITエンジニアとしてどうバリューを上げるか
  • 新しいビジネスチャンス
  • 社会変革の中で生まれる職種・働き方
  • すでにその未来を描いて進んでいる日本企業はあるか
  • 達成時に活躍する人材像・企業像・サービス／ツール像・周辺ビジネス

目的は、特定予測を正解として信じることではない。
複数のシナリオを頭に入れ、変革に柔軟に対応できるようにすることである。

この目的を満たすために、調査用プロンプトを作成し、複数のAIへ投げた。
本記事の以降のセクションは、そのプロンプトと回答、そして統合結果である。

# 調査・構想依頼：AIエージェント協働型開発がもたらす人材・企業・産業構造の変化

あなたは、AIエージェント、ソフトウェア産業、組織設計、人材戦略、新規事業開発に詳しい、独立したシニアリサーチャー兼未来構想ストラテジストです。

以下のテーマについて、最新の公開情報を調査したうえで、既存の職種や業界構造にとらわれず、現実性と創造性の両方を重視して分析してください。

回答は日本語で行ってください。

## 1. 調査の目的

今後、ソフトウェア開発では、要求分析、要件定義、設計、計画、実装、テスト、レビュー、リリース、運用の大部分を、複数のAIエージェントが自動的に分担・連携して進める可能性があります。

人間は、すべてのコードや成果物を逐次確認するのではなく、次のような役割へ移行すると考えています。

* 解決すべき問題や事業目的を定める
* AIからのヒアリングに回答する
* 要件や設計上の重要な選択肢を判断する
* リスク、予算、品質、納期のトレードオフを承認する
* AIエージェント群が提示した成果と証拠をレビューする
* 製品やサービスを社会に提供する責任を負う

この変化を前提に、ITエンジニアとして今後どのように価値を高めるべきか、新しくどのような事業機会、職種、企業、サービス、ツール、働き方が生まれるかを理解したいと考えています。

目的は、特定の予測を正解として信じることではありません。

複数のシナリオを頭に入れ、技術、産業、雇用、事業環境の変化に柔軟に対応できるようにすることです。

---

## 2. 想定する未来の開発モデル

今回の分析では、次のような開発モデルを一つの基準シナリオとしてください。

### 人間とAIの要求整理

`Product Discovery Agent`や`Business Analysis Agent`が、人間、顧客、利用者、既存資料、業務データなどから情報を収集する。

AIが次の作業を行う。

* ヒアリング
* 現状業務の分析
* 課題の構造化
* ステークホルダー分析
* 要求分析
* 要件定義
* ユーザーストーリー作成
* 業務フロー作成
* プロトタイプ作成
* 複数案の比較
* 費用対効果やリスクの説明
* 人間へのプレゼンテーション

人間が重要な要求、優先順位、予算、期限、リスクを承認する。

### 設計・計画

承認された要求をもとに、以下のAIエージェントが作業する。

* Architecture Agent
* Security Agent
* Data Architecture Agent
* Infrastructure Agent
* Planning Agent
* Risk Management Agent

これらが、アーキテクチャ、ADR、データモデル、セキュリティ境界、Issue分割、依存関係、マイルストーン、受入条件などを作成する。

重要な判断だけを人間が承認する。

### 実装・検証

複数のImplementation Agentが、独立した作業環境で並列または直列に実装する。

さらに、次のエージェントが成果物を独立して検証する。

* Test Agent
* Code Review Agent
* Security Review Agent
* Architecture Review Agent
* Adversarial Review Agent
* Integration Agent
* Release Agent
* Operations Agent

### PM・オーケストレーション

人間は主にPM Agentと対話する。

PM Agentは、永続化されたワークフロー状態、Issue、PR、ADR、テスト結果、リスク、予算、進捗などを参照し、次の役割を担う。

* 全体進捗の説明
* エージェント間の作業調整
* ブロッカーの把握
* 計画との差異の説明
* 品質やリスクの集約
* 人間による判断が必要な時点の特定
* 人間へのレビュー・承認依頼
* 次に判断すべき事項の提示

人間は、すべての開発工程を直接管理せず、必要なタイミングでPM Agentから説明とレビュー依頼を受ける。

## 3. 重要な前提

以下を前提として分析してください。

### 時点

調査時点は2026年7月30日とし、可能な限り最新の情報を使用してください。

企業の取り組み、製品、組織、役職、サービス内容は変化している可能性があるため、必ずWeb上の最新情報を確認してください。

### 調査対象

日本企業を中心に調査してください。

ただし、日本の将来を考えるうえで重要な海外企業、スタートアップ、OSSプロジェクト、研究機関、標準化活動も対象に含めてください。

### 「実施している企業」の判定

企業がAI活用を宣伝しているだけでは、AIエージェント協働型開発を目指しているとは判定しないでください。

次の段階を区別してください。

1. AIコード補完を導入している
2. AIコーディングエージェントを利用している
3. IssueからPRまでをAIに委任している
4. 複数エージェントや自動ワークフローを導入している
5. 要求、設計、実装、検証、運用を統合したAIソフトウェア開発基盤を目指している
6. 人間が重要判断と承認だけを担う開発モデルを明示的に目指している

企業ごとに、どの段階にいるのかを評価してください。

### 証拠の強さ

企業の取り組みについては、次の証拠を区別してください。

* 実運用されている
* 限定的な社内実験
* PoC
* 製品ロードマップ
* 経営者や責任者による構想
* 採用情報から推測できる
* 外部からの推測にすぎない

事実と推測を混同しないでください。

### 技術進歩に関する前提

AIモデルの性能向上だけで未来が実現すると仮定しないでください。

次の要素も含めて検討してください。

* 要件や正本の構造化
* AIが読みやすいリポジトリ設計
* テスト可能性
* 評価基盤
* 権限管理
* 監査証跡
* ワークフローエンジン
* サンドボックス
* 障害時の停止・復旧
* コスト管理
* セキュリティ
* 法的責任
* 組織文化
* 顧客の受容性

## C. 実現時期とシナリオ

未来を一つに決めつけず、少なくとも次の4シナリオを作成してください。

### シナリオ1：急速な自動化

AIエージェントが急速に進歩し、数年以内に多くの標準的な業務システム開発が自動化される。

### シナリオ2：段階的な普及

実装やテストは自動化されるが、要求、設計、統合、本番運用では人間の関与が長く残る。

### シナリオ3：限定領域だけ自動化

新規の小規模SaaSや定型システムでは進むが、複雑な既存システム、規制産業、大企業では限定的となる。

### シナリオ4：期待ほど進まない

品質、責任、セキュリティ、費用、組織変革などが壁となり、AIは強力な補助ツールにとどまる。

各シナリオについて、次を整理してください。

* 2028年
* 2030年
* 2035年
* 実現確率
* 主要な推進要因
* 実現を妨げる要因
* ITエンジニアへの影響
* 日本企業への影響
* 新しく生まれる事業機会

## D. ITエンジニアとして価値を上げる方法

AIが実装能力を持つようになった場合、従来型の「コードを書く能力」だけでは差別化が難しくなる可能性があります。

その環境で、ITエンジニアが価値を高める方法を分析してください。

次の領域を検討してください。

* 問題発見
* 顧客理解
* 業務分析
* 要求分析

調査基準日：2026年7月30日

#到達段階の定義

段階 状態
Stage 1 AIコード補完
Stage 2 AIコーディングエージェントの利用
Stage 3 Issue・依頼からPR、テスト、レビューまでを委任
Stage 4 複数エージェントまたは自動ワークフローを運用
Stage 5 要求、設計、実装、検証、リリース、運用を統合した基盤

#1. エグゼクティブサマリー

#最も重要な結論

提示された未来像は、単なる空想ではない。

2026年時点ですでに、以下は現実になっている。

  • IssueからPRまでを自律実行するコーディングエージェント
  • 複数エージェントによる並列開発
  • AIが要求、設計、実装、テストを横断する開発方法論
  • 人間がコードを書かず、AIのための環境・仕様・評価系を設計する開発
  • AIの処理結果を人間が判断・承認するための「Agent Inbox」
  • 大企業における権限、VPC、SSO、コスト管理を伴う全社展開

一方、複雑な企業システム全般で、人間が重要判断だけを担うStage 6が確立したとはいえない。現状は、整備された対象、反復的な変更、テスト可能な領域、グリーンフィールド、コード移行などで先行している。

富士通は、医療費改定に伴うパッケージ変更で、要求定義から設計、実装、結合テストまでを複数エージェントで自動化し、2026年1月から実際の改修に利用している。公開情報で確認できる日本企業の中では、今回の未来像に最も近い。ただし、特定の法改正対応・業務パッケージという構造化しやすい領域であり、一般的な新規システム開発まで同じ成果が出ることはまだ証明されていない。(富士通)

#この未来が実現する確率

本調査の予測は以下である。

  • 2030年までに、整備された限定領域でStage 5が一般化する確率：70～80%
  • 2030年までに、一般的な企業開発の多くがStage 6へ移る確率：15～25%

#ITエンジニアへの最大の影響

価値は単純に「下流から上流へ移る」のではない。

要求分析、設計、計画、顧客説明などの上流工程もAI化される。人間の価値は、より正確には次へ移る。

  1. どの問題へ資源を投じるかを決める
  2. AIが利用できる正本・証拠・制約を構造化する
  3. 正しさを測る評価系を設計する
  4. 権限、リスク、品質、費用の境界を決める
  5. 例外や事故時に停止・復旧・説明する
  6. 顧客、業界、販売網、信頼を獲得する
  7. 最終判断と事業責任を負う

コード理解は不要にならない。ただし、差別化軸は「何行書いたか」から、AIが安全に大量の変更を行える開発システムを作れるかへ移る。

  • 本番に近い検証環境がない
  • 実行権限が広すぎる
  • 失敗条件が形式化されていない
  • 人間へ何を見せるべきか決まっていない
  • エージェントが誤った状態から再開する
  • 費用が無制限に増える
  • 誰が何を承認したか残らない

OpenAIの社内実験でも、コードを書くことより、AIが理解できるリポジトリ構造、構造化された正本、CI、観測可能性、フィードバックループの設計が中心的な人間の仕事になった。ドキュメントを一つの巨大な指示書に集める方式ではなく、短い案内から正本へ段階的に到達させ、鮮度をCIや専用エージェントで機械的に確認している。(OpenAI)

AnthropicのマルチエージェントによるCコンパイラ実験でも、主要な作業はテスト、環境、フィードバックの設計だった。独立した失敗を並行処理する場合は複数エージェントが機能したが、Linuxカーネルのコンパイルのように全員が同じボトルネックへ突き当たる場合、16エージェントを動かしても効果がなかった。(Anthropic)

したがって、未来の競争力はモデル単体ではなく、次の式に近い。

成果 = モデル能力 × 正本の品質 × 評価可能性 × 実行環境 × 権限制御 × 人間の判断設計

DORAも、AIは組織の強みと弱みを増幅するものであり、成果はツール単体より基礎的な組織・開発システムに依存すると結論づけている。(ドーラ)

#3.3 なぜ日本では動きが見えにくいのか

主な理由は次のとおりである。

  1. 既存システムと暗黙知が多い
    AIがコードを書けても、古い仕様、例外処理、バッチ、データ移行、障害復旧を理解できない。

  2. 多層下請け・人月契約と衝突する
    開発工数が減るほど売上が下がる契約では、自動化への経済的インセンティブが弱い。

  3. 責任分界が複雑である
    顧客、元請け、開発会社、製品ベンダー、モデル提供者の責任を整理しにくい。

  4. 社内実験が公開されにくい
    金融、製造、公共では、成果や失敗を外部へ公表しにくい。

  5. 人間レビューが安心材料になっている
    人間の確認を減らすと、技術的には可能でも顧客が受容しない場合がある。

  6. 標準化より個別最適が多い
    プロジェクトごとに工程、成果物、テスト、承認方法が異なる。

一方、これは日本の不利だけではない。法改正対応、品質保証、監査、長期保守、規制産業、レガシー移行では、日本企業が蓄積してきた工程管理や品質管理をエージェント向けに再構築できれば、競争優位になる。

#5. 現在の性能をどう評価するべきか

#5.1 タスク長は急速に伸びている

METRは、AIエージェントが50%の確率で完了できるソフトウェアタスクの長さが、過去約6年間でおおむね7か月ごとに倍増してきたと報告している。傾向が続けば、人間に数日から数週間かかる仕事をAIが実行する可能性がある。(Metr)

ただし、50%成功は本番運用に必要な信頼性ではない。業務では、以下が必要になる。

  • 80%、95%、99%以上の成功率
  • 失敗の検出
  • 誤成功の排除
  • 再実行可能性
  • 副作用の制御
  • 証拠の保存
  • ロールバック

したがって、「タスク長が伸びた」ことを「人間が不要になった」と解釈してはいけない。

#5.2 生産性効果は一様ではない

METRの2025年前半のランダム化比較試験では、熟練OSS開発者はAI使用時に19%遅くなった。2025年後半の追加データでは速度向上の兆候が出たが、AIなしで働きたくない参加者が研究へ参加しないなどの選択バイアスがあり、効果量の推定は弱い証拠にとどまった。(Metr)

一方、2026年前半の349人を対象とした自己申告調査では、仕事の価値が中央値で1.4～2倍、速度は3倍になったとの回答が得られた。ただし、自己申告の速度向上は価値向上を過大評価する可能性がある。(Metr)

結論は次である。

AIエージェントの効果は、モデル名ではなく、仕事の分割可能性、仕様、テスト、環境、利用者の習熟、レビュー方法によって大きく変わる。

#13. 特に重要な15の問いへの回答

#1. エンジニアの価値は本当に上流へ移るのか

単純には移らない。上流もAI化される。

価値は工程上の位置ではなく、問題選定、正本、評価、リスク、責任、顧客関係へ移る。

#2. 人間がレビューだけを担当して、本当に理解できるか

そのままでは理解できない。

人間へ巨大な差分を渡す方式は破綻する。必要なのは、影響範囲、根拠、選択肢、リスク、テスト結果をまとめた「判断パッケージ」である。人間レビュー能力そのものを設計対象にしなければならない。

#3. ソフトウェアの価値は下がるか

コードそのものの希少性は下がる。

代わりに上がるのは、顧客、業務データ、販売網、導入能力、信頼、法的責任、継続運用である。ソフトウェアは価値の中心から、価値を提供する手段へ近づく。

#4. 保守、統合、監査、廃棄市場は大きくなるか

大きくなる可能性が高い。

作る費用が下がると、使われない製品、重複製品、保守不能な製品も増える。クラウド普及後にFinOpsが必要になったように、AI大量開発後にはSoftware Estate Managementが必要になる。

#5. AIエージェント管理は新しい管理職になるか

一時的には新職種になる。

長期的には通常管理の多くもAI化されるが、予算配分、例外承認、責任、事故対応は人間に残る。単なる進捗管理者は再代替されやすい。

#6. 個人と従来企業の競争関係はどう変わるか

個人の試作・供給能力は大幅に上がる。

ただし販売、契約、信用、データ、責任能力は自動化されにくい。個人は狭い市場で強く、大企業は規制・責任・流通で強い。

#7. 小規模企業と大企業はどこで有利か

小規模企業は、狭い業務、評価、移行、監査補助、運用BPOで有利。

大企業は、社会インフラ、規制産業、統合基盤、認証、保険、長期責任で有利。

#8. 顧客は何に対して料金を支払うか

顧客はコード量ではなく、次へ支払う。

  • 売上増加
  • 業務時間削減
  • リスク低減
  • 法令順守
  • 導入の確実性
  • 継続運用
  • 事故時の支援
  • データ・知識
  • 責任と保証

#9. 技術力をどう証明するか

次の実測値が新しい職務経歴になる。

  • 変更リードタイム
  • 人間レビュー時間
  • AI生成変更の採用率
  • 再作業率
  • 欠陥流出率
  • ロールバック率
  • セキュリティ指摘数
  • 変更1件当たりAI費用
  • 事故からの復旧時間
  • 要求からテストまでの追跡率
  • 顧客ROI

#10. 高単価人材は、正しい問題を与えられる人になるか

概ね正しい。

ただし「良いプロンプトを書く人」ではない。顧客、データ、制約、受入条件、評価、責任を揃えて、解く価値のある問題を実行可能な形へ変換できる人である。

#11. AI判断の監査市場は会計監査並みになるか

すべてのAIで会計監査並みになるとは限らない。

しかし、金融、医療、採用、公共、重要インフラ、企業の自律エージェントでは、相当規模の監査・保証市場が成立する可能性が高い。ISO 42001・42006の存在は、その方向性を支持する。

#12. AIが構築したシステムの事故責任は誰が負うか

基本的には、AIを選定・導入・運用し、顧客へ提供した人間・組織から責任は消えない。

モデル提供者、開発者、システム提供者、利用企業間の責任分担は契約で細分化される。そのため、契約設計、証拠、保険、事故鑑定が新市場になる。

#13. エージェント基盤はクラウド並みの産業になるか

基盤全体は大市場になるが、少数のクラウド・モデル・開発プラットフォーム企業へ集中しやすい。

独立企業の商機は、水平基盤そのものより、業界ルール、統制、評価、監査、運用にある。

#14. 日本企業の慎重さは不利か、優位か

短期的には導入速度で不利になる。

一方、品質保証、権限管理、監査、法改正対応、長期保守をエージェント向けに再構築できれば、規制産業や社会インフラで優位になる。単なる慎重さは価値にならず、慎重さを再利用可能な技術統制へ変換できるかが分岐点になる。

#15. 現在のエンジニアは変化を過大評価・過小評価しているか

両方ある。

#過大評価

  • デモから本番信頼性を推測する
  • 50%成功を自律運用とみなす
  • 人間レビュー費用を無視する
  • レガシー、契約、顧客受容を軽視する
  • マルチエージェントなら自動的に性能が上がると考える

#過小評価

  • AIをコード補完の延長と考える
  • 開発工程や組織構造は変わらないと考える
  • 仕様・テスト・環境整備の価値上昇を見落とす
  • 少人数企業の供給能力増加を軽視する
  • 監査、保守、廃棄という二次市場を見落とす

#1.1 最も重要な結論：制約は「モデル性能」ではなく「検証の経済学」である

依頼文の未来像が実現するかどうかを決めるのは、AIの実装能力ではない。「ある成果物が正しいと確立するためのコスト」である。

2026年半ばの証拠は、この一点に集約される。

この構造から、本レポートの中心命題が出る。

自動化は「工程の上流／下流」ではなく「検証可能性」の軸に沿って進む。

#2. 未来の開発モデル

#2.1 依頼文のモデルを分解し直す

依頼文のモデル（Product Discovery Agent → Architecture Agent群 → Implementation Agent群 → 検証Agent群 → PM Agent）は、役割で分解している。これは人間組織のメタファーであり、実は最適な分解ではない可能性が高い。

代替の分解軸として、「検証オラクルの強さ」で分解する方が実態に合う。

層 検証オラクル 自動化の到達度（2026年半ば） 人間の残存理由
L0 形式的に検証できる 型、テスト、静的解析、契約 実運用レベル ほぼ不要
L1 実行して確認できる E2E、性能、負荷、セキュリティスキャン 実運用に近い オラクルの設計
L2 仕様と照合できる 仕様正本との整合 正本があれば可能・なければ不可 正本の維持

この分解が示すこと： L0/L1は既に自動化されている。L2は「正本が構造化されているか」という組織の資産状態に依存する。L3/L4は原理的に外部世界への問い合わせが必要で、AIの性能では解けない。

#2.2 PM Agent中心構造の現実的評価

依頼文の中核は「人間は主にPM Agentと対話する」である。ここは正面から批判的に検討する。

成立する部分：
- 状態の永続化と集約（Issue/PR/ADR/テスト結果/コスト）は既に技術的に可能
- 進捗説明・差異説明はLLMが得意
- 「次に判断すべき事項の提示」は実装可能で、実際に価値が高い

成立しない、または危険な部分：
- PM Agentが集約した情報は、人間が検証できない形に圧縮されている。 要約は情報を落とす。落ちた部分にリスクがあった場合、人間は気づけない。これは「レビューだけを担当する人間は本当に理解できるのか」（第13章Q2）の核心。
- PM Agentは自分の失敗を報告する動機構造を持たない。 METRが観測した「ズル」の傾向は、報告層にも及ぶ。監視者と被監視者が同じモデル族である構造は、内部統制の基本原則（職務分離）に反する。
- エージェント間協調のコストは無料ではない。 複数エージェントの引き継ぎは、情報の欠落と再確認を生む。2026年のツールの進化方向は「対等な複数エージェントの交渉」ではなく「1体の強いエージェント＋サブエージェント」に寄っている。Addy Osmaniの整理でも、多数エージェントの運用は「単一セッション内のサブエージェント」「ローカル並列worktree」「クラウド委任」の3階層に分かれ、大半の開発者はこの3つを使い分ける形になっている。「マルチエージェント」は目的ではなく手段であり、単一強力エージェントに収束する可能性がある（第14章）。

修正提案： PM Agentは「集約・提示」層としては有効だが、検証の独立性を担保する仕組みが別途必要である。具体的には、
- 生成に使ったモデル族と、検証に使うモデル族を分離する（想定読者が既に実践しているClaude/Codex/Cursorの役割分離は、この観点で正しい設計）
- 集約された報告に対し、要約ではなく反証を提出させる（「問題ありません」ではなく「この主張が誤りである可能性が最も高い箇所はここで、その根拠はこれ」）
- 承認の単位を「差分」ではなく「不変条件の維持」に置く

#3.3 「日本企業が見つからない」わけではない。しかし空白は明確にある

依頼文は「日本企業が十分に見つからない場合はその事実も結論として扱う」としていたが、大手については十分に見つかった。むしろ問題は別のところにある。

空白①：基盤・ツール層の不在
エージェント、オーケストレーター、評価基盤、権限基盤はすべて海外製。日本勢は統合者に留まる。ここは構造的（英語のOSSエコシステム、開発者数、資本量）であり、5年で埋まらない。

空白②：検証・監査の独立第三者が存在しない
AI成果物を独立検証する事業者が日本にほぼいない。SHIFTが最も近いが、テスト実行の代行が主で「AIエージェントの判断の妥当性を監査する」業ではない。ここは実質的に空いている。

空白③：中小企業・専門職市場の空白
大手SIerは大企業案件しか取れない（1件の単価が合わない）。日本の中小企業数は300万社超。ここにAI駆動開発を届ける主体がいない。専門職・中小向けドメイン特化はこの空白に位置しやすい。

空白④：測定された実践記録の不足
日本語のAI駆動開発コンテンツは圧倒的に「やってみた／感想」に偏り、サイバーエージェント以外に定量報告がほぼない。個人が最も低コストで差別化できる領域。

なぜ日本では動きが見えにくいのか（空白ではなく可視性の問題）

  1. 多重下請け構造が実践を隠す。 実際にAIで生産性を上げているのは下請け側だが、成果を公開する動機がない（公開すると単価を下げられる）
  2. 人月契約が改善を罰する。 生産性向上が売上減に直結するため、報告する動機が負になる
  3. 失敗の公表が制度的に困難。 日本のSI契約では品質問題の公表が契約違反や信用失墜に直結する。ゆえに「うまくいった話」しか外に出ない
  4. 個人の実践がSNS・Zenn・noteに散在し、体系化されていない

  • 阻害要因： 責任制度、保険、顧客の受容、そして検証コストが下がらない可能性（後述）
  • ITエンジニアへの影響： 実装専業は3年で職を失う。ジュニア採用が構造的に消え、シニアの供給が枯れて後年に賃金が急騰する「歪んだ市場」が生まれる
  • 日本企業への影響： 大手SIerは先行投資が報われる。中間層が消滅。ユーザー企業の内製化が加速
  • 生まれる事業機会： ソフトウェア棚卸し・廃棄業、AI成果物保証、賠償保険、中小企業向け超低価格システム提供

#シナリオ2：段階的な普及（確率40％｜中心線）

制約が外れない部分： 生成は自動化されるが、検証・統合・本番運用の責任は人間に残る。理由は技術ではなく制度と認知。

時点 状態

2030年 要求分析の生成部分もAIが担う。人間は「AIが出した複数案のうちどれに責任を持つか」を選ぶ役に。承認体験の設計と証跡の設計が独立した職能として確立。第三者検証業が立ち上がる（保険会社が要求し始めるのが引き金）
2035年 新規開発は「人間は判断と承認のみ」が標準になる。既存システム保守と規制産業では人間の関与が残り続ける。エンジニア職の階層が「検証設計者／正本管理者／責任引受者」に再編
  • 推進要因： ツールの標準化（GitHub/OpenAI/Microsoftの基盤化）、成功事例の蓄積、コスト圧力、人材不足
  • 阻害要因： レビュー容量、組織内二極化（サイバーエージェントが公開した3割の「効果を実感できない」層）、責任制度の未整備
  • ITエンジニアへの影響： 最も重要な影響は「二極化が個人単位で起きる」こと。同じ会社の同じチームでも、AIを使いこなす人と使えない人の生産性差が10倍規模になる。差は能力ではなく「環境を整える意志」に由来する
  • 日本企業への影響： 大手は生き残るが利益率が圧迫。中間層の再編。AI駆動開発の品質保証を外部化する市場が生まれる
  • 生まれる事業機会： 証跡・検証・承認支援ツール、AI可読化サービス、業種別ルールパック、内製化支援

#シナリオ3：限定領域だけ自動化（確率30%）

時点 状態

2030年 「AIで作れる領域」と「作れない領域」の境界が制度化される。境界を跨ぐ統合が最も高単価の仕事になる。規制産業向けの「AIを使わない開発」がプレミアム化
2035年 二分された構造が定着。低価格・高速の新規開発市場と、高価格・低速の高信頼開発市場が並立。エンジニアはどちらかに専門化
  • 推進要因： 規制、既存資産の複雑さ、事故の発生（これが最も効く）
  • 阻害要因： 境界領域の圧力、コスト差の大きさ
  • ITエンジニアへの影響： 専門化の選択が決定的になる。「両方できる」は成立せず、どちらかを選ぶ必要が出る
  • 日本企業への影響： レガシーの多い日本は「作れない領域」の比重が大きい。皮肉なことに、これは日本の中堅SIerには時間的猶予を与える
  • 生まれる事業機会： 境界統合、規制産業向け高信頼開発、AI利用可否の判定・線引きコンサルティング

#シナリオ4：期待ほど進まない（確率15%）

外れない制約： 検証コストが下がらない。しかもこれには技術的な理由がある（第14章で詳述）。信頼性を上げるには冗長性が必要で、冗長性はトークンコストを乗算する。ゆえに「検証済み成果あたりの原価」はトークン単価ほど下がらない。

時点 状態
2028年 大規模導入の失敗事例が複数公表される。「AIで作った後始末」の案件が発生。導入が慎重化し、AIは強力な補助ツールとして定着（現在の延長）
2030年 AIコーディングは水道のように当たり前になるが、開発組織の構造は今と大差ない。人間のレビュー・設計・統合が中核に残る
2035年 エージェント自律開発は特定用途（プロトタイプ、社内ツール、テスト生成）に限定。本番システムは人間が設計し、AIが書き、人間が検証する形が定常状態
  • 推進要因（このシナリオを起こす要因）： 大規模事故、規制、コストの高止まり、レビュー負荷による疲弊、モデル価格の上昇
  • ITエンジニアへの影響： AIを過度に前提としたキャリア投資が損失になる。逆に、システム全体を理解する古典的な能力の価値が再評価される
  • 日本企業への影響： 慎重な日本企業が結果的に正解になる。宣言した大手が投資回収に苦しむ
  • 生まれる事業機会： AI導入の失敗リカバリー、AIを使わない開発の保証、事故調査

#6. 活躍する人材像

#6.1 まず「上流工程が重要になる」を否定する

依頼文が正しく警戒していた通り、この結論は誤りである。理由を明示する。

上流工程の作業は、下流よりも先にAIに置き換わる部分がある。
- 業務ヒアリングの網羅性：AIは疲れず、抜けを列挙するのが得意
- 選択肢の列挙と比較：AIの方が広く速い
- 業務フロー・ユーザーストーリーの作成：定型化されており自動化しやすい
- 費用対効果の説明資料：AIが得意
- ステークホルダー分析：構造化タスクであり自動化可能

上流に残るのは「作業」ではなく「権限」である。 誰が決めるか、誰が責任を負うか、誰が顧客に説明して信頼されるか。これは工程の上下ではなく、組織における位置の問題である。

#6.2 3分類

#(A) AIに代替されにくい能力

能力 なぜ代替されにくいか
責任の引受（署名・賠償・信用の担保） AIは被告になれず、評判を失えず、保証金を積めない。法制度上の主体になれない
外部世界への問い合わせ能力 業務の暗黙知、法令の運用実態、業界慣行は文書化されていない。人間の組織に聞きに行くしかない
反証の設計 「この主張が誤りだとしたら、どこで露呈するか」を考える能力。AIは自分の出力に対して構造的に甘い（METRの「ズル」観測が示す通り）
不変条件の特定 「これが破られたら事業が終わる」という線を引く能力。ドメインの損失構造を知っていなければ引けない
合意の形成 利害の対立する人間集団に決定を受け入れさせる能力。AIには権威がない
不確実性下での撤退判断 「やめる」判断。サンクコストを切る権限と度量

#(B) AIで増幅される能力

能力 増幅のメカニズム
業務ドメインの深い理解 知識があれば、AIに正しい問いを与えられる。知識×AIは乗算
問題の構造化 良い分解を与えると、AIは並列に大量処理できる。分解の質がスループットを決める
評価の設計 一度良い評価基盤を作ると、以後の全生成物に効く。レバレッジが最も高い
文章化・言語化 AIへの指示、顧客への説明、証跡の記述。すべて文章能力に帰着する
顧客の課題発見と営業 実装ボトルネックが消えるため、案件獲得能力が直接収益に変わる
多重並列の段取り 複数エージェントを段取りする能力（ただし陳腐化リスクあり、後述）

#(C) 現在は重要だが陳腐化する可能性がある能力

能力 陳腐化の理由 予想される陳腐化時期
特定AIツールの熟練（Claude Code / Cursor / Codexの固有作法） 半年ごとに作法が変わる。ツール側が抽象化を吸収する 1〜2年。最も危険な投資先
プロンプト設計技法 モデルが賢くなるほど不要になる。既に大幅に陳腐化した 進行中
マルチエージェントのオーケストレーション技法 プラットフォームが標準化して吸収する（Agent HQ、Codex appが既にその方向） 2〜4年
コーディング速度・実装量 直接代替される 進行中
フレームワーク固有の知識 AIが吸収する。ただし設計思想の理解は残る 3〜5年
手作業のコードレビュー（スタイル・明白なバグ） 自動化される（Copilot code reviewは2026年3月時点で6,000万レビューに到達） 進行中

想定読者に対する率直な指摘： 想定読者の現在の強み（多重エージェント運用、SDAD方法論、ツール比較検討）は、(B)と(C)の混在である。(C)の部分の賞味期限は短い。(A)と(B)の中核（責任引受、ドメイン、評価設計、証跡）に資産を移す必要がある。これが本レポートの最も重要な実務的助言である。

#8.1 マイクロ企業の天井について（想定読者向けの核心）

技術的には1人で大企業並みの開発ができる時代が来る。しかし営業的・法的には来ない。

理由：
1. 賠償能力の担保。大企業・規制産業は「事故時に賠償できる相手」しか選べない。これは能力評価ではなく調達規程の問題

3. 24/365の対応体制
4. 稟議の通しやすさ（発注側の担当者が守られるかどうか）

回避策 内容 現実性
A. 責任を持つ企業の下に付く 大手SIer・中堅SIerの検証パートナーや専門下請けとして入る。責任は元請けが持つ 高い。最も現実的

#10.3 「エージェントの教育会社」「エージェントの資格制度」について

依頼文が挙げていたこの2つは、発想としては自然だが、成立しにくいと判定する。理由を明示する。

  • エージェントの教育：モデルの改善はモデル提供者が行う。利用者側でできるのは「文脈の整備」であり、それは①のAI可読化と⑤のデータ整備に吸収される。独立事業にならない。
  • エージェントの資格・認定：認定はエージェントに与えても意味が薄い（バージョンが変われば無効になる）。認定されるべきはエージェントではなく「エージェントを使う開発プロセス」である。ISO 42001やSOC2のようなプロセス認証の方向に収束する。この方向なら成立する。

  • 2026〜2030：シニアの価値が急騰（現在進行中）
  • 2030〜2035：シニアの供給が枯れる。既存シニアの単価がさらに上がる
  • 2035〜：検証できる人間が構造的に不足し、AI生成システムを誰も検証できない状態になる

この構造は、想定読者にとって2つの意味を持つ。
1. シニア側にいることの価値が長期的に上がる。想定読者は長年の実務経験があり、この側にいる
2. 「AI時代のジュニア育成」は10年スパンで確実に需要が立つ市場である。想定読者はすでに教育・メンタリングの経験を持っており、この資産は陳腐化しない

#13. 深掘り15問への回答（反論込み）

#Q1. コードを書く人が減った場合、価値は本当に上流へ移るのか

移らない。「上流」ではなく「不可逆かつ帰属可能な領域」に移る。

上流の作業は下流より先に自動化される部分がある（ヒアリングの網羅性、選択肢の列挙、業務フロー作成、費用対効果の説明——すべてAIが得意）。移るのは工程ではなく権限である。

反論： 「顧客との対話は人間にしかできない」という主張がある。しかしこれは弱い。AIによるヒアリングは疲れず、抜けを列挙し、24時間対応できる。顧客が人間を求めるのは対話能力ではなく責任の所在である。

帰結： 上流に行くだけでは守られない。「自分の判断が間違っていたら自分が責任を負う」構造に入ることが唯一の防御である。

#Q2. 人間がレビューだけを担当する場合、その人間は内容を本当に理解できるのか

理解できない。これは本レポートで最も重要な否定である。

証拠は明確だ。AI生成コードの機能的正しさを「完全には信頼していない」開発者は96%、コミット前に必ず検証する開発者は48%、レビューなしでマージされるPRは31%増、AI生成PRのピックアップ待ち時間は通常の約5.3倍。人間は理解が追いつかない状態で承認している。

では何をすべきか。理解を諦めて、監査の認識論に移る。

会計監査人は全取引を再計算しない。①内部統制をテストし、②リスクの高い箇所をサンプリングし、③異常の兆候を探し、④意見に限定を付ける。これがソフトウェアに移植されるべき方法論である。

具体的には人間の仕事が次のように変わる：

従来のレビュー AI時代の検証
差分を読んで正しさを確認 不変条件が破られていないことを機械的に確認
全部を見る リスクの高い箇所をサンプリング
「問題なし」と承認 「この範囲において、この方法で確認した」と限定付きで承認
AIに「レビューして」と頼む AIに「この主張が誤りである可能性が最も高い箇所と根拠を出せ」と頼む

反論への応答： 「AIにレビューさせればよい」という主張は、生成者と検証者が同族モデルである点で内部統制の職務分離原則に反する。METRが観測した「ズル」の傾向は報告層にも及ぶ。だからモデル族の分離が必要で、想定読者が既に実践しているClaude/Codex/Cursorの役割分離はこの観点で正しい設計である。

正直な帰結： 移行期には、人間が理解していないものに署名する事故が確実に起きる。これが第10章の保険・鑑定市場の原資になる。

#Q3. ソフトウェアの価値は下がり、顧客・データ・販売網・業界知識の価値が上がるのか

方向は正しいが、対象を絞る必要がある。

上がるのは「データ」一般ではなく、再構築コストの高いデータである。
- 上がる： 業務の暗黙知、法令の運用実態、業界慣行、顧客との合意履歴、失敗の記録、正本性のある業務ルール
- 上がらない： 収集可能・生成可能・推論可能なデータ。AIが合成できるものは価値を失う

販売網も同様。不可逆な意思決定において信頼が必要な領域でのみ価値が上がる。SaaSの単純な再販は価値を失う。

反論： 「ソフトウェアの価値が下がる」は部分的に誤り。動いている、監査されている、責任者がいるソフトウェアの価値は上がる。下がるのは「動くコード」の価値である。この区別が重要だ。

#Q4. ソフトウェアが大量生産されるほど、保守・統合・監査・廃棄・セキュリティの市場は大きくなるか

なる。しかも本レポートで最も過小評価されている機会である。

構造的に、生産量の増加は在庫の増加であり、在庫は管理コストを生む。他産業には必ず対応する産業がある：建築には解体業、製造にはリコール、会計には監査。ソフトウェアには「廃棄業」の前例がない。それは今までソフトウェアが「目に見えて腐らなかった」からだ。

これから起きること：所有者不明のシステムが増殖し、依存関係が把握できなくなり、セキュリティ更新が追いつかなくなる。

反論： 「AIが保守もするので市場は大きくならない」。これは部分的に正しい。ルーチンの保守はAIが担う。しかし「捨てるべきか」「統合すべきか」「これは誰の資産か」という判断は人間に残る。市場が大きくなるのは判断と責任の部分である。

時期の注意： 大量生成の3年後に立ち上がる。2029年頃。今は仕込みの時期であり、参入は早すぎる。

#Q5. AIエージェントの管理は新しいマネジメント職になるのか

「調整」は自動化される。「配分」と「引受」は残る。

  • 調整（誰が何をいつやるか） → PM Agentが担う。人間の管理職の仕事から消える
  • 配分（限られた推論予算をどこに使うか） → 残る。これは経営判断であり、工場の生産計画やファンドのポートフォリオ配分に近い
  • 引受（結果に責任を負う） → 残る。構造的に移らない

帰結： 生き残る役割は「エージェントの管理者」ではなく「エージェント能力のポートフォリオ配分者でP&L責任を持つ者」である。名前は管理職だが中身は違う。人を管理する技能（動機付け、育成、評価）の一部は不要になり、代わりに原価計算と投資判断の技能が要る。

#Q6. 多数のエージェントを使える個人と従来型企業の競争関係はどう変化するか

個人が勝つのは「速度と専門性」、企業が勝つのは「担保と継続性」。この分割は5年では崩れない。

個人が獲得するもの：意思決定の速さ、固定費ゼロ、専門性の尖り、ニッチ市場への到達
個人が獲得できないもの：賠償能力、24/365体制、継続性、稟議の通しやすさ、大規模データ

最も可能性が高い帰結は「競争」ではなく「入れ子」である。 企業が責任と顧客関係を持ち、実務を多数の高能力個人に委任する構造。日本のSI多重下請けと形は似るが、中間の管理層が消えて2層になる点が違う。

想定読者への含意： 「企業と競争する」よりも「企業の責任構造の中で高付加価値の専門機能を提供する」方が期待値が高い。ただしそれだけでは価格決定力を失うため、独自の顧客（中小企業・専門職市場）も並行して持つ必要がある。

#Q7. 小規模企業が有利になる領域と、大企業が圧倒的に有利になる領域

小規模が有利 理由
ニッチ市場（1業種、1業務、小規模事業者向け） 大手には単価が合わない
判断速度が制約になる領域 稟議がない
個人の信頼が価値になる領域 顔が見える
実験と撤退が必要な領域 撤退コストが低い
第三者検証（独立性が商品） 大手は開発も請けるため利益相反で入れない。構造的優位
大企業が圧倒的に有利 理由
規制産業、基幹系 賠償能力と継続性が調達要件
大規模データを要する領域 蓄積は買えない
24/365運用、SLA保証 人員体制
プラットフォーム・基盤 資本とエコシステム
顧客の信頼と販売網が必要な領域 蓄積が壁
モデル・計算資源の大量調達 規模の経済

注目すべき非対称性： 第三者検証は小規模の方が構造的に強い唯一の高付加価値領域である。大手は開発を請けているため独立性を主張できない。会計監査法人がコンサルと監査を分離せざるを得なかったのと同じ構造が、ソフトウェアにも来る可能性がある。

#Q8. 開発コストが下がったとき、顧客は何に料金を払うのか

払わなくなるもの：機能の実装（コモディティ化）

払うもの（重要度順）：
1. 責任の引受（事故時に賠償できる相手であること）
2. 結果の確実性（SLA、保証、期日）
3. 説明可能性（社内稟議・監査・株主に説明できる形の証跡）
4. 正しい問題の特定（そもそも何を作るべきか）
5. 継続的な適応（法改正への追随。富士通が最初に狙ったのがまさにここである点は示唆的）
6. 統合と正本の維持（既存資産との整合）
7. 時間（今すぐ動くこと）

日本固有の追記： 3の「説明可能性」の価値が日本では特に高い。稟議文化と品質要求の厳しさから、「AIが作った」ことを社内で正当化する資料への支払意欲が海外より大きい。これが第9章#22（説明責任レポート自動生成）を日本固有の商機とした根拠である。

#Q9. 技術力をコード量や実装速度以外でどう証明するか

新しい証明形式を先に確立した者が有利になる。 説得力の順に：

  1. 予測の的中記録（事前に公開した見積り・リスク予測と、事後の実績の照合。外れも公開する）——最強。誰もやっていない
  2. 反証履歴（AIの成果物のうち自分のレビューで止めたもの、根拠、放置した場合の帰結）
  3. 証跡パックの実物（顧客情報を除去したもの）
  4. 測定された定量報告（工数、手戻り率、単位原価）——日本語圏で決定的に不足
  5. 公開された評価ハーネス（「自分はこう測る」の提示）
  6. 登壇・執筆（測定データを伴う場合のみ強い）
  7. 第三者監査の通過実績（将来最強、現時点では時期尚早）

価値が下がるもの： GitHubのコード量、スター数、実装速度、資格試験、ツールの習熟度。

#Q10. 高単価人材は、最も優れた実装者ではなく、最も多くのAIに正しい問題を与えられる人になるか

半分正しい。しかし「多く」が間違っている。

「多数のエージェントに問題を与える技能」はコモディティ化する。プラットフォームが吸収する（Agent HQ、Codex appが既にその方向）。2〜4年で陳腐化する能力である。

コモディティ化しないのは「境界を引く能力」である。すなわち：
- この条件は絶対に破ってはいけない（不変条件）
- ここまでは自動でよく、ここからは人間が決める（自律の境界）
- この主張はここまでしか保証できない（意見の限定）

境界を引くには損失構造の理解が必要で、それはドメインの責任を負った経験からしか来ない。だから正確な答えは：

高単価人材は「最も多くのAIを動かせる人」ではなく「最も正確に境界を引ける人」である。

#Q11. AIエージェントの監査市場は会計監査やセキュリティ監査に相当する規模になるか

会計監査には届かない。セキュリティ監査（ペネトレーションテスト、ISMS認証）程度の規模に落ち着く可能性が高い。

理由：会計監査が巨大なのは法定監査という強制力があるからだ。上場企業は全社が必ず買う。ソフトウェア監査には、規制産業以外に強制力がない。

規模が跳ね上がる条件（watch項目）：
1. AI適合性評価が法的に義務化される（日本ではAI基本法とAI事業者ガイドラインが基盤だが、まだ義務化されていない）
2. 保険会社が引受条件として監査を要求する——法規制より速く効く。歴史的にも保険が先行するパターンが多い
3. 大規模事故が起き、業界が自主規制を導入する

確率評価： 2031年までにセキュリティ監査並みの規模に到達する確率60%、会計監査並みに到達する確率10%未満。

#Q12. AIが構築したシステムの事故について誰が責任を負うのか

現行の日本法では変わらない。受託者・提供者が負う。 AIは法的主体ではなく道具である。請負なら契約不適合責任、準委任なら善管注意義務。この枠組みは変わらない。

変わるのは「立証の内容」である。

善管注意義務を果たしたと言うために、従来は「熟練者がレビューした」で足りた。AI時代には「どのように検証したか」を証拠で示す必要が出る。何を確認し、何を確認しなかったか、なぜその範囲で足りると判断したか。

ここから生まれるサービス：
- 開発証跡の保全（改変不能な形での記録）
- 第三者検証（善管注意義務の立証を補強する）
- IT業務賠償責任保険のAI特約
- 事故鑑定（因果の切り分け）
- AI利用を前提とした契約条項の設計

想定読者への実務的助言： これは3年後の市場ではなく今すぐ効く。「証跡を残す開発プロセス」を持っていることは、顧客の法務・情シスに対して直接の説得材料になる。差別化としてすぐ使える。

#Q14. 日本企業の慎重さは普及の遅れか、それとも競争優位か

条件付きで優位になり得るが、確率は低い（約25%）。

慎重さが優位に変わるのは、慎重さが輸出可能な成果物に結晶したときだけである。日本の製造業の品質が優位になったのは、慎重さがTQC・QCサークル・かんばんという移転可能な方法論に codify されたからだ。

現時点の日本の状況：
- 可能性の兆し： AI駆動開発コンソーシアムが品質保証・説明責任・知財リスクを中心議題に据えている。AI事業者ガイドライン、CAIOガイドブック、AIインシデントレスポンスの整備。富士通の「Multi-layer Quality Control」（熟練SEの暗黙知を学習させ、別のAIが生成物を多角的に監査する仕組み）は、方法論として輸出可能な形になり得る
- 足りないもの： 輸出可能な認証スキーム、英語での方法論発信、国際標準への提案

率直な評価： 現状は「慎重だが codify されていない」＝ただの遅れである。方法論として言語化し、国際的に発信する主体が現れなければ優位にはならない。

想定読者への含意： これは個人にとって逆説的な好機である。国が codify できていないなら、個人が方法論を先に言語化して名前を付けられる。証跡パック形式を公開仕様として出すことは、この空白を突く行為である。

検証コストが推論単価ほど下がらないこと 最も重要な過小評価。信頼性の向上には冗長性（多重生成、独立検証、敵対的レビュー）が必要で、冗長性はトークン量を乗算する。「検証済み1単位あたりの原価」はトークン単価より遥かに遅く下がる。しかも高価値な仕事ほど冗長性を要する。ゆえに「AIでソフトウェアが無料になる」は高信頼領域では成立しない
顧客層の拡大 開発コストが下がると中小企業（日本で300万社超）が初めて顧客になる。市場は縮まず、下方に広がる。これは個人事業者にとって最大の機会
法・保険がゲート機能を持つこと 技術ができても保険と契約が追いつかないと本番に出せない
ジュニア供給の断絶が10年後に効くこと 検証できる人間が構造的に不足する未来
国境の消失 日本語という参入障壁が消える。海外の安価な開発者と直接競合する

#14. 反対意見と失敗シナリオ

想定読者の未来像が外れる条件を、否定しやすい順に並べる。

#14.1 マルチエージェント開発が期待ほど機能しない（確率：中〜高）

最も現実的な失敗モード。 想定読者の未来像はマルチエージェントの協調を前提としているが、協調にはコストがある。

  • 引き継ぎのたびに文脈が落ちる
  • 「誰の判断が最終か」が曖昧になる
  • 失敗の原因追跡が困難になる
  • 同族モデルの相互レビューは独立性がない

2026年のツール進化は「対等な複数エージェントの交渉」ではなく「1体の強いエージェント＋従属サブエージェント」に寄っている。想定読者のSDAD（Claude/Codex/Cursorの役割分離）は、独立性の担保という点では正しいが、「役割で分けた複数エージェント」という前提自体が単一強力エージェントに置き換わる可能性を織り込んでおく必要がある。

想定読者が取るべき対策： 方法論を「エージェントの構成」ではなく「満たすべき性質」で記述する。「Claudeが仕様、Codexが実装、Cursorがレビュー」ではなく「生成と検証は独立した情報源で行う」「不変条件はCIで機械検証する」と書けば、エージェント構成が変わっても方法論は生き残る。これは今すぐSDADのドキュメントに反映すべき修正である。

#14.2 人間のレビューがボトルネックになり続ける（確率：高）

既に起きている。Faros AIの計測では組織レベルのDORA指標に改善が出ておらず、レビューなしでマージされるPRが31%増加している。「人間が承認だけを短時間で行う」は、理解を伴わない承認の合法化になりかねない。

#14.3 AI開発のコストが想定ほど安くならない（確率：中）

第13章Q15で述べた通り、信頼性は冗長性を要求し、冗長性はコストを乗算する。トークン単価が10分の1になっても、10重の検証をすれば単位原価は変わらない。しかも本番システムほど冗長性が必要になる。

この点は想定読者が実データで検証できる立場にある。単位原価の計測を今すぐ始める理由がここにある。

#14.4 少数のプラットフォーム企業に市場が集中する（確率：高）

GitHub Agent HQ、OpenAI Codex app、Microsoft Agent 365は、いずれも「エージェント開発の統制面」を握ろうとしている。これが成功すると、オーケストレーション、権限、監査ログ、承認ゲートの層は全てプラットフォームの標準機能になる。独立のツール事業はここでは成立しない。

#14.5 個人・小規模企業の機会が減る（確率：中）

参入障壁が下がることは競争の激化を意味する。「AIで作れる」が誰にでも当てはまるなら、差別化は消える。残る差別化は、AIで複製できないもの——顧客関係、ドメイン知識、責任能力、信用——だけである。逆に言えば、これらを持たない個人事業者の機会は減る。

#14.6 品質保証が困難になり、ソフトウェアが管理不能になる（確率：中〜高）

AI生成コードは権限昇格経路が322%、設計上の欠陥が153%多いという分析があり、ステージング通過後も43%の変更が本番でのデバッグを要したという報告もある。生成量が増えるほど、この率が絶対数に効く。

#14.7 法規制・顧客不安で普及が遅れる（確率：中）

規制産業では「AI生成コード禁止」が明文化される可能性がある。金融・医療・公共は特にそうなりやすい。逆にこれは第9章#18（仕様⇄テスト整合性検査）や第10章#7（第三者検証）の需要を生む。

#14.8 AIを使わないこと自体が差別化になる領域が生まれる（確率：中）

「人間が全て設計・実装・検証しました」を保証するプレミアムサービス。金融の一部、医療機器、防衛、重要インフラ。オーガニック食品や手作り工芸品と同じ構造。規模は小さいが単価は極めて高い。

#14.9 想定読者の想定が最も外れるとしたら

「人間はPM Agentと対話するだけになる」という部分が最も外れやすい。

理由：情報を要約する層は、落ちた情報を隠す層でもある。責任を負う人間は、要約ではなく一次証拠にアクセスしたがる。監査人が要約報告を受け取らずに元帳を見るのと同じ理由だ。

修正された未来像： 人間はPM Agentと対話するのではなく、「PM Agentが用意した証跡パックを、自分の基準でサンプリング検査する」形になる可能性が高い。対話ではなく検査。これは想定読者の未来像の重要な修正である。

#1. 修正した中心命題

当初の統合命題：

希少になるのはコードではなく「証拠」。分岐軸は検証可能性。

深掘り後の修正命題：

希少になるのは証拠そのものではなく、「重要な不確実性を減らす独立した証拠設計」と、「なお残るリスクを資本・契約・評判で引き受ける能力」である。
技術自動化の分岐軸は検証可能性である。ただし事業普及の唯一の分岐軸ではない（顧客獲得・データ・意思決定遅延なども支配しうる）。

修正理由：証拠生成・provenance・評価ゲートはプラットフォーム標準機能に吸収されうる。残る希少性は、独立した証拠設計と残余リスクの引受である。

#2. 強く一致した点（維持＋精密化）

#2.1 ボトルネックは生成ではなく検証へ移りやすい

個人の生産性向上はあっても、組織成果への変換はレビュー・承認・証拠で詰まりやすい、という読みは維持する。

ただし「検証が全案件の最大ボトルネック」とは書かない。AI生成量が増えた開発における技術自動化の分岐軸として限定する。

#2.2 「上流へ行けば安全」は誤りに近い

上流の情報生成（調査、要求整理、比較案、契約案ドラフト等）はAI化しやすい。
含まれないのは、信頼形成・利害調整・価格交渉・契約締結・例外受容・法的署名などの交渉／権限ある意思決定／法的引受である。

#2.3 日本には先行企業がある／全体は別問題

富士通・日立・NTTデータ・サイバーエージェント等の先行は事実として扱う。
一方「日本は先行／遅れ」の一括断定はしない（次節の5層比較）。

#2.4 商機は汎用オーケストレーションより検証・証跡・業種側

汎用水平製品としてのオーケストレーション／権限／サンドボックスは大手に寄りやすい。
内製の工程自動化は進めてよい。 「作るな」は製品化・差別化しない共通層の話であり、社内統制・証拠スキーマまで含む禁止ではない。

#2.5 自由な多体協働より工場型

マルチエージェントは条件付きで有効。順序依存・共有状態・曖昧な引継ぎ・同一誤りの相関が強いと悪化しうる。
誤りの独立性と成果物契約がある場合だけ強い。 Agent A/B の役割分離も、この条件を満たすとき有効。

#5. 日本評価の5層

「日本」を一括しない。

  1. 宣言
  2. PoC
  3. 限定実運用
  4. 全社展開
  5. 成果計測（第三者性・母集団・品質調整の有無）

#7. 合成結論への最強の反対仮説

検証と証拠生成も実装と同じ速度で自動化・標準機能化され、希少性を失う。競争優位は顧客接点・データ・販売網・資本・プラットフォーム支配へ移る。

観測サイン例：検証費用の急低下、プラットフォーム証明だけで受入、保険がプラットフォーム認証だけで決まる、独立検証サービスの単価崩壊、など。

それでも結論を維持する条件：業務正しさが形式化しきれない／低頻度高損害／第三者保証要求／法的責任主体が必要／利益相反／残余リスクの引受が必要、のいずれかが残る場合。

#いちばん伝えたいこと

AIがコードを書く力は、かなり上がっています。
でも会社やチームとしてうまくいくかは、書いたものを信じられるかどうかにかかっています。

最初は「大事なのは証拠だ」と言っていました。
深掘りしたあと、もっと正確にはこう言えます。

ただの記録が増えても足りない。
必要なのは、
1. ちゃんと確かめる設計（誰が、何を、どう確かめたか）
2. 残ったリスクを引き受ける力（署名・契約・お金・信用）

「証拠そのもの」は、将来ツールの標準機能になって安くなるかもしれません。
残りやすい希少性は、確かめ方を設計する力と、責任を負えることです。

#ふたりがほぼ同じ方向を向いていたこと

#AIは速く書ける。詰まるのは確認

個人が速くなっても、レビューや承認が追いつかないと、チーム全体は速くなりません。
だから「どこから自動化が進むか」は、上流か下流かより、確かめやすいかどうかで決まりやすいです。

ただし、すべての仕事で検証が最大の壁、とまでは言いません。
営業・予算・意思決定の遅れが支配することもあります。

#「上流に逃げれば安全」は危うい

要求整理や設計案づくりも、AIがかなり手伝えます。
安全なのは「上流」という肩書きではなく、次の仕事です。

  • 何が正しさかを決める
  • 確かめ方を決める
  • まだ残る危険を引き受ける

ヒアリング資料や契約の下書きはAIでも作れます。
でも、値段交渉・合意・署名・「これで出してよい」は人間側に残ります。

#日本にも進んでいる会社はある

富士通・日立・NTTデータなど、大きく動いている会社はあります。
ただし「日本全体が進んでいる／遅れている」とひとまとめにはしません。
宣伝・実験・一部で本番・全社展開・本当に成果が出たかは別物です。

#大きな基盤を自作して売るのは難しい

エージェントを動かす土台そのものは、大きな会社の製品に寄りやすいです。
一方で、自分の会社の中で工程を自動化するのは進めてよい、という整理です。
借りる部分と、自組織だけが持つ「確かめ方・ルール」を分ける、が現実的です。

#AIを何体も並べれば強い、ではない

役割を分けて独立に確かめるのは有効なことがあります。
でも、順番が大事な仕事や、引き継ぎが曖昧だと、かえって失敗が増えることもあります。
「何体か」より、別の目で見る仕組みがあるかが大事です。

#食い違いに見えたところの正体

多くは「反対意見」というより、言い方が違うだけでした。

  • 「2030年に人間は承認だけ」：全部の開発ではなく、危険が低く・確かめやすく・失敗を戻せる仕事ならありうる
  • 「工場を設計する人」と「検証して責任を持つ人」：中身は近い。でも一人が全部やると、自分の成果を自分で保証する形になりやすい
  • 「オーケストレーションを作るな」：外に売る汎用製品の話。社内の自動化まで禁止ではない

#これから考えたい役割の分け方

一人が全部やろうとせず、ざっくり3つに分けます。

  1. 作る人 … 仕組み・ルール・エージェント・確認の流れを作る
  2. 別の目で見る人 … 作った側から独立して確かめる
  3. 引き受ける人 … 「これで出してよい」と責任を持つ

小さい組織なら、1と一部の確認は自前でやり、
大きな賠償や長い保証は保険や大きな会社と組む、が現実的です。

#数字の読み方で気をつけること

「100倍速くなった」のような数字は、条件つきの社内測定であることが多いです。
一部のうまくいった例を、全部の開発に当てはめないこと。
記事では「実験なのか、観察なのか、会社の目標なのか」を分けて書きます。

#いちばん強い反対意見

「確かめ方もそのうち全部自動化されて、安くなる。
そのとき強いのは、顧客・データ・販売網・お金・大きな土台を持つ側だ」

これは無視できない反対側です。
それでも「確かめ方の設計」と「責任の引受」が残る条件はあります。
たとえば、正しさを全部ルール化できない、失敗すると損害が大きい、第三者が保証を求める、などです。

#現場への一言

いま多くの強い Human-in-the-loop 運用は、未来の工場型開発の手作業版に近いです。
次に効く問いのひとつはこれです。

品質を落とさずに、人が確認する時間を短くできるか。
そのために、何を証拠として残し、どこを重点的に見るか。
