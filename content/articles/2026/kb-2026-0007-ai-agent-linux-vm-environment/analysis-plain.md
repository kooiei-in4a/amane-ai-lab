# わかりやすく言うと

今回やったことは、AIに開発させる「作業机」をWindows PCから別のLinux VMへ移した、ということです。

結果はかなり良好でした。

Windows PCは人間がClaude、Codex、Cursorなどへ指示を出す場所として使い、実際のRepository、Docker、Build、TestはLinux VM側へ置きます。すると、AIが重い処理をしても普段のPCへの影響を減らせます。

それ以上に良かったのは、開発環境がPCに依存しなくなったことです。別のPCから操作しても、AIが使う開発環境は同じVMです。

# 安全面で良かったこと

AIへ自律的に開発させるには、かなりの操作権限が必要です。

その権限を普段使っているPCへ直接渡す代わりに、専用VMの中で動かします。

VMの中ではGit、Docker、Build、Testなどを自由に使わせます。一方、VMの外、特にLocal LANなどへは必要以上に出られないようにします。

つまり、「AIを何もできないようにする」のではなく、「自由に動ける範囲を箱で囲う」考え方です。

# 複数AIとも相性が良かった

Claude、Codex、Cursorなど、違うAIエージェントを使っても、実際の作業場所を同じLinux VMへ揃えられます。

Git worktreeを使えば、同じProjectでも実装用とレビュー用の作業場所を分けられます。DockerもProjectごとに名前空間を分ければ、複数作業を同時に動かしやすくなります。

このため、マルチエージェントを使う場合は「Agentごとに環境を作る」より、「開発環境ごとにVMを1台作り、そのVMを複数Agentから使う」方が分かりやすいケースがあります。

# ProxmoxとHyper-V

今回はProxmox VEとMicrosoft Hyper-Vの両方で試しました。

FirewallやSnapshotの方法は違いますが、Agent VMとして必要な考え方はほぼ共通でした。

そのため今後は、共通のAgent VM仕様を1つ作り、Proxmox用とHyper-V用の設定だけを別に持つ形が良さそうです。

# まだ残っていること

一番大きいのはVM構築の自動化です。

新しいAgent VMが必要になったとき、毎回手作業で作るのではなく、設定から再生成できるようにしたいと考えています。

OpenCodeも候補ですが、今回欲しいRemote SSHの使い方はまだ正式構成へ採用していません。状況が変わったら再確認します。

最終的には「壊れたVMを直す」のではなく、「壊れたら同じ構成のVMを作り直す」運用を目指します。
