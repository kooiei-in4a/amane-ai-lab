# 3つのAI調査の比較と統合

## 1. 資料の正本関係

記事化にあたり、資料の更新関係を次のように整理しました。

- 主たる調査プロンプトを、実際に入力した指示の正本とします。
- ChatGPT、Gemini Pro、Gemini思考の3ファイルを、AI回答の正本とします。
- 「純粋マージ」は、3回答を論点別に並べた詳細な統合資料です。
- 「明らかな矛盾点」は、統合時に解消できなかった問題を抽出した独立レビューです。
- 「統合要約」は、純粋マージと矛盾点を短くした派生資料です。

純粋マージと統合要約は、元の回答を置き換える正本ではありません。数値や結論が異なる場合は、元回答と矛盾点レビューへ戻って判断します。

## 2. 3回答の共通認識

3回答は、細部では大きく食い違いますが、実務上の候補群と導入上の論点については一定の共通点があります。

### 2.1 候補は数系列へ収束する

3回答を横断すると、主に次の系列が有力候補として残ります。

| 役割 | 回答群で繰り返し挙がった候補 | 統合上の扱い |
| --- | --- | --- |
| 主力・価格性能 | DeepSeek系列 | 実API検証の中核候補 |
| 日本語・法人運用 | Qwen系列 | 現行の正式モデルIDを再確認して候補化 |
| 長時間エージェント | GLM系列 | Tool Callingと長期タスクの検証候補 |
| 低価格処理 | DeepSeekの高速・低価格系列 | バッチと補助モデルの候補 |
| 高難度・巨大文脈 | Kimi系列 | 高価格を許容する比較枠 |
| 補欠・マルチモーダル | MiniMax系列 | 1回答中心のため追加検証枠 |

ここで重要なのは、系列名の一致と、同一モデルの一致は別だという点です。特にQwenとMiniMaxは、回答ごとに異なる世代や用途のモデルを代表として選んでいます。

### 2.2 初期比較と本番採用を分ける

3回答は程度の差はあるものの、OpenRouterなどの第三者APIが初期比較に便利だと評価しています。複数モデルを同じ形式で呼び出し、日本のカードで少額から検証しやすいためです。

一方、本番では次を固定し直す必要があります。

- 正確なモデルIDまたはsnapshot
- 実際の推論Provider
- データ処理地域
- 保存期間、学習利用、Prompt Cache
- DPA、ZDR、SLA
- レート制限と廃止通知
- フォールバック時の送信先

したがって、「PoCで便利な接続経路」と「本番で採用する契約経路」は同じでなくて構いません。

### 2.3 Cursorで動くことと公式保証は別

回答群はOpenAI互換エンドポイントによる接続可能性を評価していますが、CursorのCustom API Key、Base URL Override、Composer、Agent機能のどこまで動くかについては一致していません。

実務では次を分けて確認する必要があります。

1. 単純なChat Completionが呼べるか
2. ストリーミングが動くか
3. Tool Callingが正しく往復するか
4. reasoning固有フィールドを扱えるか
5. Cursorが公式に保証しているか
6. Cline、Roo Code、Continueなら安定するか

「接続できた」だけで、IDEの全機能に対応すると判断してはいけません。

### 2.4 セキュリティはモデル開発元だけでは決まらない

同じモデルでも、公式API、第三者Router、第三国ホスト、国内ホスト、セルフホストでデータ経路は変わります。

そのため、「中国製だから危険」「第三者APIだから安全」「オープンウェイトだから安全」という単純な分類は不十分です。評価対象は、モデルだけでなく、契約主体、Router、実推論ホスト、リージョン、ログ、キャッシュ、サブプロセッサーです。

## 3. 回答間の主要な相違点

### 3.1 Qwenの比較対象が同じではない

3回答はQwen系列を高く評価していますが、比較対象としているモデルが異なります。汎用主力、最大性能モデル、コード特化モデルを同じランキングへ入れているため、点数を平均したり「Qwenは何位」と一括りにしたりできません。

採用前には、次の枠ごとに現行モデルを1つずつ固定する必要があります。

- 汎用・エージェント主力
- コード特化
- 低価格補助
- 日本または国際リージョンで利用できるモデル
- セルフホスト可能なモデル

### 3.2 DeepSeekの契約条件と出力上限

DeepSeekについては、価格性能比が高いという評価は共通しています。しかし、次が一致していません。

- 日本発行カードが利用できるか
- 最低チャージと無料枠
- 最大出力が数十万トークンか、数千から数万トークンか
- JSON Schemaが完全対応か部分対応か
- 学習不使用、ログ保存、ZDRの関係

最大出力の差は、単なる誤差ではありません。長いパッチやレポートを1回で生成できるか、エージェントが何回に分けて作業するかに直結します。モデルの理論上限、公式API上限、Provider上限を分けて確認する必要があります。

### 3.3 GLMの価格、最大出力、契約経路

GLMについては、長時間エージェントとTool Callingへの評価は共通しています。一方、価格と最大出力には大きな差があります。また、Z.ai海外版と中国国内向けBigModelの契約条件が混ざっている可能性があります。

「GLM-5.2」という名前だけでは不十分で、次を一組として記録しなければ比較できません。

- API提供元
- モデルID
- プラン名
- 割引期間
- リージョン
- 最大出力
- 決済通貨
- KYC条件

### 3.4 Kimiの契約条件と文脈上限

Kimiについては、高難度・巨大文脈向けで話題性が高いという評価は概ね共通しています。しかし、公式APIを日本から直接契約できるか、中国電話番号やAlipayが必要か、最大コンテキストと最大出力がどこまでかは一致しません。

この状態では、Kimiを主力として予算化するのではなく、第三者APIによる限定テストから始めるのが安全です。

### 3.5 MiniMaxは世代が揃っていない

一つの回答は新しいM3系列を高く評価し、別回答は旧世代のText-01を扱っています。同一条件の比較ではないため、MiniMaxは共通上位ではなく、補欠候補として現行モデルを改めて確認するのが妥当です。

## 4. なぜ相違が生じたのか

相違の原因は、単純な「どのAIが正しいか」だけでは説明できません。

### 4.1 モデル世代が異なる

同じ開発元でも、汎用、Coder、Flash、Max、Plusなど役割が違います。系列名だけで統合すると、価格も性能も文脈長も混ざります。

### 4.2 Providerが異なる

公式APIとOpenRouterでは、価格、最大出力、速度、レート制限、データ所在地が異なる場合があります。同じモデル名でも、推論ホストが違えば運用品質は同じではありません。

### 4.3 公開日、API開始日、ウェイト公開日が混ざる

発表日とAPI提供開始日が別の日であったり、タイムゾーン差があったりします。日付が1日違う場合は、どのイベントの日付かを分ける必要があります。

### 4.4 公称性能と第三者実績が混ざる

開発元のベンチマーク、第三者ベンチマーク、コミュニティの評判、API利用量は別の証拠です。公称値だけで実務性能を確定できません。

### 4.5 アカウント作成後にしか確認できない条件がある

カード承認、本人確認、最低チャージ、請求書払い、残高期限などは、公開ページだけでは確定できない場合があります。Web調査だけで断定すると誤りやすい領域です。

## 5. 根拠が比較的強い主張

今回の資料から比較的強く言えるのは、次のような「評価方法」に関する結論です。

- 性能だけでなく、日本からの契約、API互換性、安定性、データ条件を合わせて評価すべき
- モデル開発元とAPI提供元を分けて記録すべき
- 人気と話題性を分けるべき
- 初期比較と本番契約を分けるべき
- 同一課題で実APIを比較し、build/test結果まで確認すべき
- モデルID、Provider、実行日、費用、エラーを記録すべき
- 機密コードではZDR、DPA、保存期間、データ所在地を確認すべき

これらは、3回答と統合資料で繰り返し支持され、特定のモデル名が変わっても有効です。

## 6. 根拠が弱い、または未検証の主張

次は、記事公開時点では確定情報として扱いません。

- 2026年の各モデルの正確な性能順位
- 特定モデルがGPTやClaudeの特定世代を上回るという断定
- 日本カードが必ず通るという断定
- 最大出力やコンテキストの大きな数値
- APIデータが一律に学習・保存されないという断定
- Cursorの全機能で直接利用できるという断定
- GitHub Star、ダウンロード数、APIシェアから実務品質まで推定すること
- 今後6か月から1年の勝者予測

これらは、一次情報の再確認または実API試験が必要です。

## 8. 見落とされやすい論点

### 8.1 フォールバックで送信先が変わる

Routerの自動フォールバックは可用性を上げますが、機密コードの送信先が別Providerへ変わる可能性があります。Provider固定の有無を確認すべきです。

### 8.2 Prompt Cacheはログ保存と別

キャッシュは価格を下げますが、入力の一部が保持される可能性があります。「学習に使わない」「ログを保存しない」「キャッシュしない」は別々に確認します。

### 8.3 `latest`は再現性を壊す

モデルが自動更新されると、同じプロンプトでも結果が変わります。業務導入ではsnapshotを固定し、廃止通知と回帰試験を運用へ組み込みます。

### 8.4 出力コードの知財と品質

オープンウェイトでも、生成コードのライセンス適合性や正しさは保証されません。build、test、静的解析、ライセンススキャン、人間レビューが必要です。

### 8.5 長いコンテキストは性能保証ではない

入力可能なトークン数が大きくても、遠い位置の情報を正しく参照できるとは限りません。リポジトリ理解は、実際の依存関係問題で評価すべきです。

## 9. 実務へ適用する条件

### Phase 0: 一次情報の固定

候補ごとに次を公式ページまたは契約画面で確認します。

- 正確なモデルID
- 料金と確認日
- コンテキストと最大出力
- Tool Calling、JSON Schema、Streaming
- 利用可能リージョン
- 日本カード、KYC、請求通貨
- 保存、学習、キャッシュ、DPA、ZDR、SLA
- 廃止予定とsnapshot

### Phase 1: 統一Providerで横比較

OpenRouterなどを使う場合は、同じProvider条件で候補を比較します。比較しやすさを優先する段階であり、本番経路の確定ではありません。

### Phase 2: 公式または固定Providerで再試験

上位候補は、実際に採用するProviderで同じ課題を再実行します。Router経由と公式APIで結果、速度、上限、費用が同じとは限りません。

### Phase 3: セキュリティ・法務ゲート

機密度に応じて、送信禁止データ、マスキング、Provider固定、ログ、DPA、障害通知、退役時の移行手順を決めます。

### Phase 4: 本番運用

モデルIDを固定し、回帰試験、予算アラート、429/5xx監視、フォールバック、廃止通知を運用します。

## 10. 共通APIテスト

資料の共通部分を採用すると、最低限次の10課題を同一条件で試します。

1. 単一関数生成
2. 再現テスト付きバグ修正
3. 複数ファイル変更計画
4. 重大度付きコードレビュー
5. 単体テスト生成
6. 日本語仕様書からの実装
7. 複数ステップのTool Calling
8. 厳格なJSON Schema出力
9. 日本語指示による既存コード変更
10. 長いリポジトリ文脈の理解

各課題で、成功、build/test、指示遵守、Tool引数、JSON適合、応答時間、トークン数、費用、APIエラー、再試行、人間修正量を記録します。

## 11. 残る不確実性とリスク

- 候補モデル自体が短期間で更新・廃止される
- 価格や割引が変更される
- 公開仕様と実API上限が異なる
- 日本からのカード・本人確認がアカウントごとに異なる
- Routerが利用する推論ホストが変わる
- 長時間エージェントの失敗が高額な再試行につながる
- 契約上、顧客コードを送れない
- 実測前のランキングが採用バイアスになる

## 12. 人間が最終判断すべき事項

1. 送信してよいデータの機密区分
2. 中国または第三国への越境移転を許容するか
3. 必要なDPA、ZDR、SLA、監査証跡
4. 月額予算と障害時の許容時間
5. 公式API、固定Provider、Router、セルフホストのどれを採用するか
6. モデル更新を自動で受け入れるか、snapshotを固定するか
7. PoCの合格基準と主力・補助・レビュー用の役割分担
