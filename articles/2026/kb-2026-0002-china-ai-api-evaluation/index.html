検討に至った背景

#検討に至った背景

#なぜこの調査を行ったのか

中国企業・中国系研究組織が開発するAIモデルは、低価格、長いコンテキスト、コーディング性能、オープンウェイトなどを理由に、開発用途の候補として扱われることが増えています。一方、日本から実務で使う場合は、性能ランキングだけでは判断できません。

実際の導入では、次の条件が同時に成立する必要があります。

  • 日本の個人または法人が契約・決済できる
  • APIを既存プログラムや開発ツールへ接続できる
  • Tool Callingや構造化出力が安定して動く
  • 価格と応答性能が業務量に見合う
  • 入力したソースコードや業務情報の保存・学習・移転条件を説明できる
  • モデル更新や提供終了に備えて再現性を確保できる

このため、単なるベンチマーク順位ではなく、「日本から現実的に導入できるか」を中心に複数のAIへ同じ調査を依頼しました。

#今回の中心的な問い

中心的な問いは、次の2つです。

  1. 提供された3つのAI調査から、どの中国製AIモデルを導入候補として残せるか
  2. 回答間の矛盾や未確認情報がある状態で、どこまで結論を出してよいか

#対象範囲

対象は、API経由で利用でき、次の用途に関係する中国製AIモデルです。

  • コード生成、修正、レビュー、テスト生成
  • Cline、Roo Code、Continueなどの開発エージェント
  • 独自のAIエージェントや業務システムへの組み込み
  • 低価格な大量処理
  • 長い仕様書やリポジトリの解析
  • 日本からの契約、決済、運用

#対象外

次は今回の記事では確定しません。

  • 各モデルの絶対的な性能順位
  • 日本発行カードが実際に承認されるか
  • 個別アカウントの本人確認結果
  • 契約書、DPA、ZDR、保存期間の法的評価
  • 実APIを使った速度、障害率、Tool Calling成功率
  • セルフホストに必要な正確な設備費
  • 2026年7月31日以後の価格やモデル更新

#読み方

AI回答内のモデル名、料金、仕様、ランキングは、回答時点の調査結果または主張です。この記事では、複数回答が一致しただけで事実認定せず、一次情報と実APIで再確認すべき項目を明確に分けます。

# 中国製AIモデルのAPI利用・開発用途調査

## 1. 調査目的

中国企業・中国系研究組織が開発したAIモデルのうち、API経由でプログラムから利用でき、ソフトウェア開発、コーディング支援、AIエージェント、業務システムへの組み込みに適したモデルを調査してください。

単なるモデル性能ランキングではなく、以下を判断できる実務的な調査結果を作成してください。

* 日本から現実的に契約・決済・利用できるか
* APIを既存プログラムへ組み込みやすいか
* Cursor、Cline、Continueなどの開発ツールや、OpenAI API互換クライアントから利用できるか
* コーディングやエージェント用途に適しているか
* 価格、性能、安定性、導入難易度のバランスがよいか
* 現在人気がある、または話題になっているモデルはどれか
* 一時的な話題ではなく、今後も利用候補として残りそうか

調査時点の最新情報をWebで確認し、古いモデル情報や過去の価格を最新情報として扱わないでください。

少なくとも、以下の開発元・モデル系列を調査対象候補に含めてください。

* DeepSeek

* Baidu / ERNIE
* Tencent / Hunyuan

上記以外にも、調査時点で人気、話題性、性能、価格競争力のある中国製モデルがあれば追加してください。

ただし、次のモデルは主対象から除外して構いません。

* API提供が確認できないモデル
* 中国国内の特殊な契約が必須で、日本からの利用が現実的でないモデル
* 旧世代で、後継モデルに実質的に置き換えられているモデル
* 画像・動画・音声生成専用で、プログラム開発用途に適さないモデル
* 情報が極端に少なく、利用可否を検証できないモデル

除外した主要モデルがある場合は、除外理由を簡潔に示してください。

---

## 3. 「中国製」の定義

本調査では、以下のいずれかに該当するモデルを中国製として扱ってください。

* 中国に本社を置く企業が開発している
* 中国系企業グループが主要な開発主体である
* 中国の研究組織が中心となって開発している

APIの提供元が米国や第三国の事業者であっても、モデル自体が中国製であれば対象に含めてください。

---

## 4. API提供経路の区別

同じモデルでも、API提供経路によって価格、契約条件、データ管理、可用性が異なるため、以下を明確に区別してください。

1. 開発元の公式API
2. 中国国内向け公式クラウドAPI
3. 海外向け公式API
4. OpenRouterなどの第三者API
5. Alibaba Cloud、SiliconFlow、Together AI、Fireworks AIなどの外部ホスティング
6. セルフホスト可能なオープンウェイトモデル

公式APIと第三者APIは、原則として別行または別欄で比較してください。

「モデルの開発元」と「APIの提供元」を混同しないでください。

## 6. 人気度・話題性の調査

人気度と話題性は別の指標として評価してください。

### 6.1 人気度

人気度は、実際の利用規模や継続的な支持を表します。

可能な範囲で以下を確認してください。

* API利用量
* OpenRouterなどでの利用順位
* Hugging Faceのダウンロード数
* Hugging FaceのLike数
* GitHubのStar数
* GitHubのFork数
* 関連リポジトリの活動状況
* モデル対応サービスの数
* Cline、Continue、Open WebUI、LiteLLMなどでの対応状況
* 企業での採用事例
* クラウド事業者での提供状況
* 開発者コミュニティの規模
* 継続的なアップデート頻度

### 6.2 話題性

話題性は、調査時点の直近3か月から6か月を中心に評価してください。

* 新モデル発表による注目
* ニュース報道
* X、Reddit、Hacker Newsなどでの言及
* 中国国内SNSや技術コミュニティでの反響
* ベンチマーク結果への反響
* 価格破壊としての注目
* オープンウェイト公開による注目
* Cursorなど著名サービスとの関係
* 大規模な資金調達や提携
* 障害、規制、セキュリティ問題など否定的な話題

### 6.3 評価方法

人気度と話題性を、それぞれ次の5段階で評価してください。

* 5：非常に高い
* 4：高い
* 3：中程度
* 2：限定的
* 1：低い

必ず評価根拠を併記してください。

単なるニュース件数だけで評価せず、実利用の裏付けを確認してください。

「公開直後で話題性は高いが、実利用はまだ少ない」など、人気度と話題性が異なる場合は明示してください。

### 6.4 トレンドの持続性

次の3段階で評価してください。

* 高：今後も主要な利用候補として残る可能性が高い
* 中：一定の利用は続くが、競合次第で存在感が低下する可能性がある
* 低：一時的な話題、または後継モデルに置き換えられる可能性が高い

根拠も簡潔に記載してください。

ただし、これは試食会の会場をそろえるためです。本番契約をOpenRouterに決めたという意味ではありません。

#3. 実際に使う契約先でもう一度試す

候補を絞ったら、公式APIや固定したProviderで同じ試験をします。入口が変わると、速度や制限が変わる可能性があるからです。

#4. 機密情報の扱いを決める

次を確認できないサービスへ、顧客情報や非公開コードを送らないようにします。

  • どこで処理するか
  • 何日保存するか
  • 学習に使うか
  • キャッシュするか
  • 契約書やDPAがあるか
  • 問題が起きた時に連絡が来るか

#5. 合格点を先に決める

「なんとなく良かった」ではなく、たとえば次を決めます。

  • 10課題のうち何件成功すればよいか
  • 作ったコードがbuild/testを通る割合
  • Tool Callingの正確さ
  • JSONが指定形式を守る割合
  • 1課題あたりの費用
  • 人間が直す時間
  • 429やタイムアウトの回数

#私たちが採るべき暫定方針

現時点では、1つのモデルへ決め打ちするより、役割別に候補を残す方が合理的です。

役割 暫定候補
主力の価格性能 DeepSeek系列
日本語・企業運用 Qwenの現行国際向けモデル
長時間エージェント GLM系列
安い大量処理 DeepSeekの低価格系列
難しい最終比較 Kimi系列
追加比較 MiniMaxの現行モデル

これは採用決定ではありません。試験へ進める候補一覧です。

#利点

  • 1つのAI回答の間違いに引きずられにくい
  • 価格だけでなく、契約や安全性も見られる
  • 主力、補助、レビュー用に役割を分けられる
  • モデルが終了しても切り替えやすい
  • 実際の費用と人間の修正時間を比べられる

#欠点

  • 比較試験に手間がかかる
  • 複数Providerの契約管理が必要になる
  • モデルの更新が速く、結果が古くなりやすい
  • 機密情報を扱う場合は法務・セキュリティ確認が増える
  • 最初から「これが1位」と言う記事より結論が地味に見える

しかし、業務システムの導入判断では、派手な順位より、再現できる試験と説明できる契約条件の方が重要です。

#統合結論

#中心的な問いへの回答

提供された3つのAI調査だけから、単一の「最優秀中国製AIモデル」を確定することはできません。

DeepSeek、Qwen、GLM、Kimiなどの系列は共通して有力候補に挙がりましたが、正確なモデルID、価格、最大出力、日本からの契約条件、データ保持条件に重大な不一致が残っています。そのため、この記事で採用する結論は次の通りです。

モデルランキングをそのまま採用せず、役割別の候補群を作り、正確なモデルID・Provider・データ条件を固定した実API試験で採否を決める。

#採用する暫定候補

現時点では、次の役割分担で検証へ進むのが妥当です。

  1. 主力・価格性能: DeepSeekの現行高性能系列
  2. 日本語・法人運用: Qwenの現行国際向け汎用系列
  3. 長時間エージェント: GLMの現行エージェント向け系列
  4. 低価格バッチ: DeepSeekの現行低価格・高速系列
  5. 高難度比較: Kimiの現行フロンティア系列
  6. 追加比較: MiniMaxの現行長文・マルチモーダル系列

資料内の具体的なモデル名は候補探索に使いますが、採用前に公式の現行モデル一覧で再確認します。

#推奨する導入手順

#1. 公式情報を固定する

候補ごとに、モデルID、料金、最大出力、リージョン、契約条件、保存・学習・キャッシュ、DPA、ZDR、SLA、廃止予定を確認します。

#2. 第三者APIで横比較する

PoCでは、同じインターフェースと同じテスト課題で比較します。第三者APIは比較の摩擦を減らしますが、安全性や本番適性を自動的に保証するものではありません。

#3. 採用経路で再試験する

上位候補は、公式APIまたは本番で固定するProviderを使って再試験します。速度、上限、Tool Calling、障害率、データ経路が変わる可能性があります。

#4. セキュリティ・法務ゲートを通す

機密コードや顧客情報を扱う場合は、送信禁止情報、マスキング、Provider固定、保存期間、契約文書、越境移転、障害通知を人間が承認します。

#5. 役割別に採用する

1モデルですべてを処理するのではなく、主力、低価格補助、高難度レビュー、フォールバックに分けます。

#この結論を採用する理由

  • 3回答の共通部分を利用できる
  • 矛盾を都合よく解消せず、未確認事項として残せる
  • モデル名が更新されても評価方法を再利用できる
  • 性能だけでなく、契約、運用、セキュリティを判断へ含められる
  • 実際のbuild/test、Tool Calling、費用、人間修正量で比較できる

#採用しなかった考え方

#1. 総合点1位をそのまま採用する

採点対象のモデル世代やProviderが揃っておらず、点数の前提が異なるため採用しません。

#2. 3回答の多数決で事実を決める

複数AIが同じ誤情報を参照する可能性があります。一致は調査優先度を上げますが、一次情報の代わりにはなりません。

#3. 第三者APIを常に最安全とみなす

比較には便利ですが、Routerと実推論ホストの両方を評価する必要があります。自動ルーティングで送信先が変わることもあります。

#4. オープンウェイトなら安全とみなす

自社管理環境で運用すればデータ境界を管理しやすくなりますが、GPU、運用、脆弱性対応、モデル更新、ライセンス確認の負担があります。

#確信度

  • 評価方法と導入手順: 高
  • 候補系列の選定: 中
  • 資料内の具体的な価格・上限・契約条件: 低から中
  • 単一モデルの最終順位: 低

#適用条件

この結論は、日本からAPIを契約し、コーディング支援、AIエージェント、業務システムへ組み込む用途を想定しています。中国国内だけで完結するサービス、画像・動画専用モデル、特定産業の専用契約は別評価が必要です。

#残余リスク

  • 調査直後にモデルや価格が更新される
  • 公開仕様と実APIの挙動が異なる
  • カード承認やKYCが利用者ごとに異なる
  • Providerの自動切替でデータ送信先が変わる
  • 長いコンテキストが実際の理解精度へ結びつかない
  • 生成コードに不具合やライセンス問題が残る
  • 契約文書が機密コードの送信を許可しない
  • モデル廃止で再現性が失われる

#次に取るべき行動

  1. 各系列から現行モデルを1件ずつ選び、正式モデルIDとProviderを確定する
  2. 価格、最大出力、Tool Calling、JSON Schema、契約・データ条件を一次情報で確認する
  3. 同一の10課題を最低3回ずつ実行する
  4. build/test、成功率、費用、APIエラー、人間修正量を記録する
  5. 上位候補を採用予定Providerで再試験する
  6. 機密区分とセキュリティ・法務ゲートを決める
  7. 主力、補助、レビュー、フォールバックの役割を決定する

#結論を一言でいうと

#いま1社・1モデルに決めない

3つのAI調査は、DeepSeek、Qwen、GLMなどを有力候補として挙げました。しかし、値段、契約方法、一度に出力できる量、データの扱いについて、回答が大きく食い違っています。

そのため、今すぐ「このモデルが1位」と決めるのではなく、候補を役割別に残して少額の実験をするのが安全です。

#推奨案

#主力候補

安さとコーディング性能の候補として、DeepSeekの現行高性能モデルを試します。

#日本企業向け候補

日本語、国際契約、リージョン、法人運用を重視し、Qwenの現行国際向けモデルを試します。資料に書かれた名称をそのまま使わず、公式ページで現在のモデルIDを確認します。

#長時間エージェント候補

複数のツールを長く使う仕事では、GLMの現行モデルを比較します。ただし、値段と最大出力の記述が食い違うため、契約前に確認します。

#安い大量処理

分類、前処理、簡単なレビューなどは、DeepSeekの低価格・高速モデルを比較します。

#難しい仕事の比較枠

他モデルが失敗する難しい課題や大きなリポジトリでは、Kimiの現行高性能モデルを限定的に試します。高価になりやすいため、通常の大量処理には使いません。

#進め方

  1. 公式ページで、現在使える正確なモデル名と値段を確認する
  2. OpenRouterなどで同じ課題を試し、候補を絞る
  3. 本番で使う公式APIまたは固定Providerでもう一度試す
  4. 顧客情報や非公開コードを送ってよい契約か確認する
  5. 主力、安い補助、難しいレビュー、予備の4役に分ける

#メリット

  • 誤ったランキングで契約する危険を減らせる
  • 実際にかかる費用と人間の手直し時間を比べられる
  • 1つのサービスが止まっても切り替えやすい
  • 安いモデルと高性能モデルを使い分けられる
  • セキュリティや契約条件を説明しやすい

#デメリット

  • 比較試験の準備と記録に手間がかかる
  • 複数のAPIキーや請求を管理する必要がある
  • モデル更新が速く、定期的な再試験が必要になる
  • 機密情報を扱う場合は、法務とセキュリティ確認が増える
  • 最初から1位を決める方法より、決定まで時間がかかる

#経営・営業の判断ポイント

値段の安さだけでなく、次を確認してください。

  • 顧客との契約上、コードやデータを外部AIへ送ってよいか
  • データがどの国で処理・保存されるか
  • 問題発生時の連絡や保証があるか
  • モデルが終了した時に切り替えられるか
  • 人間の修正時間を含めても安いか
  • 日本語の仕様や業務ルールを正しく扱えるか

#最終判断

PoCでは複数モデルを同じ条件で比較し、本番ではモデルID、Provider、データ条件を固定する。

これが、今回の資料から導ける最も安全で実務的な結論です。
