## 1.3 【一致③】人間が「確認だけ」になる条件は、能力ではなく体制で決まる

両者が挙げた条件はほぼ同一だった。統合すると5条件になる。

| # | 条件 | B の表現 | A の対応概念 |
|---|---|---|---|
| 1 | **正本が明確** | ADR / 承認済み仕様 / Issue / API契約 / データモデル | L2（仕様正本との照合）が成立する状態。「正本のドリフト検出」が未整備 |

### A が追加した検証オラクル階層（B にない枠組み）

| 層 | 検証オラクル | 2026年半ばの自動化到達度 | 人間が残る理由 |
|---|---|---|---|
| L0 形式的に検証できる | 型、テスト、静的解析、契約 | 実運用レベル | ほぼ不要 |
| L1 実行して確認できる | E2E、性能、負荷、セキュリティスキャン | 実運用に近い | オラクルの設計 |

| L3 業務と照合するしかない | 現場の暗黙知、法令解釈、業界慣行 | 不可 | **知識の所在が人間側** |
| L4 結果が出るまで分からない | 事業判断、UX、市場適合 | 不可 | **責任の所在** |

**〔統合判断〕** B の5条件は、A の L2 を L0/L1 に落とし込むための実装手順として読める。**両者を重ねると「未来の開発モデルの本質は、エージェントを何体並べるかではなく、L2 をどれだけ L0/L1 に落とし込めるか」という単一の命題になる。**

# 第II部：2つの回答が食い違った点と裁定

## 2.1 【対立①】実現確率 ― 数字は倍近く違う

### B の予測（確率評価）

| 時点 | 状態 | 実現確率 |
|---|---|---|
| 2028年末 | 小規模な標準SaaSを、設計・実装・テスト・PRまでほぼ全自動 | **75%** |
| 2030年末 | 整備された既存システムで、Issueから本番候補まで全自動 | **70%** |
| 2030年末 | 人間は重要ADR、マージ、本番反映の承認だけ | **60%** |
| 2032年末 | 複数サービスを含む中規模システムをAIチームが継続運用 | **65%** |
| 2032年末 | 高規制・高リスクシステムでも人間は最終確認だけ | **30%** |
| 2035年以降 | 大部分の一般的な業務システムでAI実装が標準 | **80%以上** |

### A の予測（シナリオ分岐）

| シナリオ | 内容 | 確率 |
|---|---|---|
| 1：急速な自動化 | 数年内に標準的業務システム開発の多くが自動化 | **15%** |
| 2：段階的普及 | 実装・テストは自動化、要求・統合・本番運用に人間が長く残る | **40%（中心線）** |
| 3：限定領域のみ | 新規小規模SaaSと定型は進む。複雑既存・規制・大企業は限定的 | **30%** |
| 4：期待ほど進まない | 品質・責任・費用・組織が壁となり強力な補助ツールに留まる | **15%** |

A の判定：**「人間は重要判断と承認のみ」モデルは、シナリオ1でのみ2020年代に成立する。**シナリオ2/3では2030年頃に**新規開発の一部領域**で成立し、既存システム保守・規制産業では2035年でも部分的にしか成立しない。

### 〔統合判断〕この差は見かけほど大きくない

**差の主因は「対象範囲の定義」である。**

- B の「2028年末75%」は **小規模な標準SaaS** に限定されている。これは A のシナリオ2の2028年像（「実装・単体テスト・定型改修はほぼ自動化」）およびシナリオ3の2028年像（「新規SaaS、社内ツール、定型帳票システムは1人〜数人で作れる」）と**実質的に一致する**。
- 真に対立しているのは1行だけ：**「2030年末に人間は承認だけ」**。B が60%、A は同時期の同条件を実質40%未満と見ている。
- さらに A は、B が数値化していない**質的な反論**を置いている（→ 2.3）。

**採用する見方：** B の確率表は「限定領域について」読み、A のシナリオ表は「市場全体について」読む。両者を重ねると、**2028〜2030年に "AIで作れる領域" と "作れない領域" の境界が可視化され、境界の位置そのものが事業機会になる**という像が得られる。

## 2.2 【対立②】次の一手 ― 正面から衝突している

これが本統合で**最も重要な対立**である。

| ソース | 提言 |
|---|---|
| B | Koo の手動工程制御を**ワークフローエンジンに落とせば**、Issue作成 → Agent A起動 → Draft PR → Agent B起動 → 指摘分類 → 修正エージェント起動 → CI → Human承認待ち まで自動化できる。「次の段階は工程制御を仕様化して自動化すること」 |
| A | **避けること #1：汎用オーケストレーション基盤・ワークフローエンジンの開発。** GitHub / OpenAI / Microsoft に確実に潰される。**時間の完全な損失**。同 #2：エージェント権限・ID基盤。#3：サンドボックス・実行環境 |

### 〔統合判断〕「自社内製」と「製品化」を分ければ両立する

両者は**同じ対象について逆のことを言っているのではない**。

| 目的 | 判定 | 根拠 |
|---|---|---|
| **自社の工程制御を自動化する（内部利用）** | **B が正しい。実行すべき** | A も「まだ人間が行っている工程」の存在自体は認めており、避けるべきと言っているのは"事業として基盤を作ること"。内製の自動化は A の12.1〜12.2の行動計画（証跡パック生成ツール、評価ハーネス、不変条件アナライザ）と矛盾しない |
| **それを汎用製品として売る** | **A が正しい。やめるべき** | GitHub Agent HQ / OpenAI Codex app / Microsoft Agent 365 が既にこの層を標準機能化しつつある（A：14.4 確率「高」） |
| **その過程で得た測定データ・方法論を公開する** | **両者と整合。最優先** | B の「工程の仕様化」の副産物が、A の「証跡パック形式」「単位原価データ」そのものになる |

**したがって行動指針は：工程制御は自動化する。ただし成果物として外に出すのはエンジンではなく、"型" と "データ" である。**

## 2.3 【対立③】人間の承認 ― A は B のフロー図の一点を危険とみなす

B は開発フローの最後に「人間：確認・承認」を素直に置いている。A はこれを名指しで否定した。

> **短時間で行える承認は、理解を伴わない承認である。**「人間が承認だけを短時間で行う」は、**事故の設計図**になりかねない。（A：11.1、14.2）

> **人間はPM Agentと対話するのではなく、「PM Agentが用意した証跡パックを、自分の基準でサンプリング検査する」形になる可能性が高い。対話ではなく検査。**（A：14.9 ― A自身が「依頼者の未来像の最も外れやすい部分」と指摘）

**A が提示した代替：監査の認識論への移行**

会計監査人は全取引を再計算しない。①内部統制をテストし、②リスクの高い箇所をサンプリングし、③異常の兆候を探し、④意見に**限定を付ける**。

| 従来のレビュー | AI時代の検証 |
|---|---|
| 差分を読んで正しさを確認 | **不変条件が破られていないことを機械的に確認** |
| 全部を見る | **リスクの高い箇所をサンプリング** |
| 「問題なし」と承認 | **「この範囲において、この方法で確認した」と限定付きで承認** |
| AIに「レビューして」と頼む | **AIに「この主張が誤りである可能性が最も高い箇所と根拠を出せ」と頼む** |

**〔統合判断〕B のフロー図に、A の修正を差し込んだ統合版が以下になる。**

```text
人間：目的・制約・予算・受入方針を承認
  ↓
Portfolio / Product Agent
  ↓
Architecture Agent ── ADR作成／リスク分類 ──▶ 【ゲート1】Human承認（不可逆な決定のみ）
  ↓
Planning Agent ── Issue分割／依存分析／実装順序
  ↓
Implementation Agent（複数・独立worktree）── 実装／テスト／Draft PR
  ↓
Review Agent群 ── 仕様／セキュリティ／migration／adversarial／回帰
  │  ※ 生成側と別モデル族であること（同族相互レビューは独立性なし）
  │  ※ 出力は「問題ありません」ではなく「この主張が誤りである可能性が最も高い箇所と根拠」
  ↓
Integration Agent ── 指摘対応／CI確認／◆証跡パック生成◆／マージ候補作成
  ↓
【ゲート2】人間：★対話ではなくサンプリング検査★
  ├─ 不変条件がCIで機械検証されていることの確認（全件を読まない）
  ├─ リスク上位箇所のみ一次証拠まで下りる
  └─ 「この範囲において、この方法で確認した」と限定付き承認
  ↓
Deploy / Monitoring / Rollback Agent
  ↓
【ゲート3】production 変更は別承認／destructive operation は停止
```

**◆ 印が A の追加。★ 印が A による B の修正。** 変更点は2つ：**証跡パックの生成を工程に組み込むこと**と、**承認を「対話」から「限定付きサンプリング検査」に置き換えること**。

## 2.4 【対立④】焦点 ― 実は相補的

| | B (ChatGPT) | A (Claude) |
|---|---|---|
| 問い | **How**：どうやって自動化するか | **What / Why**：何をポジションとして取るか、なぜそれが残るか |

## 2.5 【見かけの矛盾】OpenAI の「コードは全部AI」事例と「配備率一桁%」

| B の主張 | A の主張 |
|---|---|

## 4.3 A のみが提示した論点（B に対応物がないが重要度が高い）

### (1) 残るのは「上流」ではなく「引受」

| 層 | 内容 | 2030年の希少性 |
|---|---|---|
| 生成層 | 案を出す、書く、実装する、選択肢を列挙する | ほぼゼロ |
| 検証層 | 反証を設計する、証拠を要求する、不変条件を守らせる | 高い |
| **引受層** | 署名する、責任を負う、賠償能力を担保する、顧客の信頼を背負う | **最も高い（構造的にAIに移らない）** |

**AIが構造的にできないのは判断ではない。結果を引き受けることである。** AIは被告になれず、解雇されず、評判を失わず、保証金を積めない。

### (2) マイクロ企業の天井

**技術的には1人で大企業並みの開発ができる時代が来る。しかし営業的・法的には来ない。** 理由：①賠償能力の担保（調達規程の問題であり能力評価ではない） ②継続性 ③24/365体制 ④稟議の通しやすさ。

回避策は3つのみ：**A. 責任を持つ企業の下に付く**（現実性：高） **B. 責任を商品化する**＝IT業務賠償責任保険に加入し提案書に明記（現実性：中〜高・今すぐ可能） **C. 相手を選ぶ**＝中小企業・士業（現実性：高・既存路線）。**BとCを今すぐ、Aを1年以内に1件。**

### (3) 日本市場の4つの空白

①基盤・ツール層の不在（構造的・5年で埋まらない） ②**検証・監査の独立第三者が存在しない**（実質的に空いている） ③**中小企業・士業市場の空白**（300万社超・大手は単価が合わず取れない） ④**測定された実践記録の不足**（個人が最も低コストで差別化できる）

### (4) ジュニア供給の断絶（どの言説にも欠けている論点）

実装で学ぶ経路が消えると、10年後に**検証できる人間がいなくなる**。2026〜2030でシニアの価値が急騰し、2030〜2035でシニアの供給が枯れ、2035〜は「AI生成システムを誰も検証できない状態」に向かう。**Koo は25年の経験を持つシニア側におり、かつ教育・メンタリング経験を持つ。この資産は陳腐化しない。**

### (5) 体感は信頼できない

LinearB の810万PR・4,800組織超の分析では、開発者は**20%速くなったと感じながら実際には19%遅くなっており、体感と実測に39ポイントの差**があった。→ 単位原価の実測が必須である最大の根拠。

- 「AI駆動開発が速い人」ではない ― **1年で全員が名乗る**
- 「上流ができる人」ではない ― **上流の作業はAIに移る**

根拠：①4シナリオのどれが来ても価値が残る ②AIに再代替されにくい（責任は法的主体にしか帰属しない） ③**小規模事業者に構造的優位がある唯一の高付加価値領域**（大手は開発を請けるため独立性を主張できない） ④日本市場に固有の需要（稟議文化・説明責任・レガシー規模・中小企業の空白） ⑤既存資産（ADR・多重レビュー・SDAD・25年の経験・士業ターゲット）がそのまま原材料になる

## 5.5 やらないこと（A の禁止事項・B と衝突する箇所は 2.2 の裁定に従う）

1. 汎用オーケストレーション基盤・ワークフローエンジンの**開発（製品として）** ― GitHub / OpenAI / Microsoft に潰される
2. エージェント権限・ID基盤の開発 ― IAM大手の領域
3. サンドボックス・実行環境の開発 ― クラウド事業者の領域
4. 特定ツールの作法への深い投資 ― 半年で陳腐化
5. 「AI駆動開発が速い」を売りにすること ― 1年で差別化にならない
6. 業種を早く広げること ― 2業種目で優位が消える
7. 人月単価での受注比率を上げること
8. 規制産業・大企業基幹系への単独参入 ― 元請けの下に付く形以外は構造的に無理
9. AI導入コンサルティングの一般提供 ― 既に激戦
