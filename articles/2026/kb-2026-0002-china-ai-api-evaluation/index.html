検討に至った背景

#検討に至った背景

#なぜこの調査を行ったのか

中国企業・中国系研究組織が開発するAIモデルは、低価格、長いコンテキスト、コーディング性能、オープンウェイトなどを理由に、開発用途の候補として扱われることが増えています。一方、日本から実務で使う場合は、性能ランキングだけでは判断できません。

実際の導入では、次の条件が同時に成立する必要があります。

  • 日本の個人または法人が契約・決済できる
  • APIを既存プログラムや開発ツールへ接続できる
  • Tool Callingや構造化出力が安定して動く
  • 価格と応答性能が業務量に見合う
  • 入力したソースコードや業務情報の保存・学習・移転条件を説明できる
  • モデル更新や提供終了に備えて再現性を確保できる

このため、単なるベンチマーク順位ではなく、「日本から現実的に導入できるか」を中心に複数のAIへ同じ調査を依頼しました。

#今回の中心的な問い

中心的な問いは、次の2つです。

  1. 提供された3つのAI調査から、どの中国製AIモデルを導入候補として残せるか
  2. 回答間の矛盾や未確認情報がある状態で、どこまで結論を出してよいか

公開後の2026-08-01追記は、「個人のコーディング用途で、いま試す現行モデルIDはどれか」に答える追加確認です。調査時点の慎重な法人導入判断を置き換えるものではありません。

#入力資料の構成

#対象範囲

対象は、API経由で利用でき、次の用途に関係する中国製AIモデルです。

  • コード生成、修正、レビュー、テスト生成
  • Cline、Roo Code、Continueなどの開発エージェント
  • 独自のAIエージェントや業務システムへの組み込み
  • 低価格な大量処理
  • 長い仕様書やリポジトリの解析
  • 日本からの契約、決済、運用

#対象外

次は今回の記事では確定しません。

  • 各モデルの絶対的な性能順位
  • 日本発行カードが実際に承認されるか
  • 個別アカウントの本人確認結果
  • 契約書、DPA、ZDR、保存期間の法的評価
  • 実APIを使った速度、障害率、Tool Calling成功率
  • セルフホストに必要な正確な設備費
  • 2026-08-01追記で名前を挙げた一部モデル以外の価格・モデル更新、および今後の変更

名前を挙げた中国製モデルについては、2026-08-01の追記で公開価格やモデルIDを再確認しています。それ以外のモデル・Providerや、その後の更新は未確認のままです。

#読み方

この記事は、根拠の異なる3層で読んでください。

  1. 第1層（3調査の統合）: 評価方法と中国製系列の候補群。単一の勝者は決めません。
  2. 第2層（個人開発向け追記）: DeepSeek／GLM／Kimiなど特定中国製モデルの一次情報による価格・接続整理。
  3. 第3層（コーディング再比較）: 公表ベンチマークとAPI従量単価によるCoding Agent向け再比較。費用・性能の文脈ではGPT-5.6やClaude Opus 5など中国製以外も含みます。

AI回答内のモデル名、料金、仕様、ランキングは、回答時点の調査結果または主張です。複数回答が一致しただけで事実認定せず、一次情報と実APIで再確認すべき項目を明確に分けます。後ろの追記は前の調査回答を上書きした正本ではなく、公開後の追加確認です。

# 中国製AIモデルのAPI利用・開発用途調査

## 1. 調査目的

中国企業・中国系研究組織が開発したAIモデルのうち、API経由でプログラムから利用でき、ソフトウェア開発、コーディング支援、AIエージェント、業務システムへの組み込みに適したモデルを調査してください。

単なるモデル性能ランキングではなく、以下を判断できる実務的な調査結果を作成してください。

* 日本から現実的に契約・決済・利用できるか
* APIを既存プログラムへ組み込みやすいか
* Cursor、Cline、Continueなどの開発ツールや、OpenAI API互換クライアントから利用できるか
* コーディングやエージェント用途に適しているか
* 価格、性能、安定性、導入難易度のバランスがよいか
* 現在人気がある、または話題になっているモデルはどれか
* 一時的な話題ではなく、今後も利用候補として残りそうか

調査時点の最新情報をWebで確認し、古いモデル情報や過去の価格を最新情報として扱わないでください。

ただし、次のモデルは主対象から除外して構いません。

## 3. 「中国製」の定義

本調査では、以下のいずれかに該当するモデルを中国製として扱ってください。

* 中国に本社を置く企業が開発している
* 中国系企業グループが主要な開発主体である
* 中国の研究組織が中心となって開発している

APIの提供元が米国や第三国の事業者であっても、モデル自体が中国製であれば対象に含めてください。

## 4. API提供経路の区別

同じモデルでも、API提供経路によって価格、契約条件、データ管理、可用性が異なるため、以下を明確に区別してください。

1. 開発元の公式API
2. 中国国内向け公式クラウドAPI
3. 海外向け公式API
4. OpenRouterなどの第三者API
5. Alibaba Cloud、SiliconFlow、Together AI、Fireworks AIなどの外部ホスティング
6. セルフホスト可能なオープンウェイトモデル

公式APIと第三者APIは、原則として別行または別欄で比較してください。

「モデルの開発元」と「APIの提供元」を混同しないでください。

* 新モデル発表による注目

人気度と話題性を、それぞれ次の5段階で評価してください。

* 5：非常に高い
* 4：高い
* 3：中程度
* 2：限定的
* 1：低い

#4. なぜ相違が生じたのか

相違の原因は、単純な「どのAIが正しいか」だけでは説明できません。

#4.1 モデル世代が異なる

同じ開発元でも、汎用、Coder、Flash、Max、Plusなど役割が違います。系列名だけで統合すると、価格も性能も文脈長も混ざります。

#4.2 Providerが異なる

公式APIとOpenRouterでは、価格、最大出力、速度、レート制限、データ所在地が異なる場合があります。同じモデル名でも、推論ホストが違えば運用品質は同じではありません。

#4.3 公開日、API開始日、ウェイト公開日が混ざる

発表日とAPI提供開始日が別の日であったり、タイムゾーン差があったりします。日付が1日違う場合は、どのイベントの日付かを分ける必要があります。

#4.4 公称性能と第三者実績が混ざる

開発元のベンチマーク、第三者ベンチマーク、コミュニティの評判、API利用量は別の証拠です。公称値だけで実務性能を確定できません。

#4.5 アカウント作成後にしか確認できない条件がある

カード承認、本人確認、最低チャージ、請求書払い、残高期限などは、公開ページだけでは確定できない場合があります。Web調査だけで断定すると誤りやすい領域です。

#5. 根拠が比較的強い主張

今回の資料から比較的強く言えるのは、次のような「評価方法」に関する結論です。

  • 性能だけでなく、日本からの契約、API互換性、安定性、データ条件を合わせて評価すべき
  • モデル開発元とAPI提供元を分けて記録すべき
  • 人気と話題性を分けるべき
  • 初期比較と本番契約を分けるべき
  • 同一課題で実APIを比較し、build/test結果まで確認すべき
  • モデルID、Provider、実行日、費用、エラーを記録すべき
  • 機密コードではZDR、DPA、保存期間、データ所在地を確認すべき

これらは、3回答と統合資料で繰り返し支持され、特定のモデル名が変わっても有効です。

#8. 見落とされやすい論点

#8.1 フォールバックで送信先が変わる

Routerの自動フォールバックは可用性を上げますが、機密コードの送信先が別Providerへ変わる可能性があります。Provider固定の有無を確認すべきです。

#8.2 Prompt Cacheはログ保存と別

キャッシュは価格を下げますが、入力の一部が保持される可能性があります。「学習に使わない」「ログを保存しない」「キャッシュしない」は別々に確認します。

#8.3 latestは再現性を壊す

モデルが自動更新されると、同じプロンプトでも結果が変わります。業務導入ではsnapshotを固定し、廃止通知と回帰試験を運用へ組み込みます。

#8.4 出力コードの知財と品質

オープンウェイトでも、生成コードのライセンス適合性や正しさは保証されません。build、test、静的解析、ライセンススキャン、人間レビューが必要です。

#8.5 長いコンテキストは性能保証ではない

入力可能なトークン数が大きくても、遠い位置の情報を正しく参照できるとは限りません。リポジトリ理解は、実際の依存関係問題で評価すべきです。

#9. 実務へ適用する条件

上位候補は、実際に採用するProviderで同じ課題を再実行します。Router経由と公式APIで結果、速度、上限、費用が同じとは限りません。

#Phase 3: セキュリティ・法務ゲート

機密度に応じて、送信禁止データ、マスキング、Provider固定、ログ、DPA、障害通知、退役時の移行手順を決めます。

#Phase 4: 本番運用

モデルIDを固定し、回帰試験、予算アラート、429/5xx監視、フォールバック、廃止通知を運用します。

#なぜ、そのまま順位を信じられないのか

#同じ会社でも、比べている商品が違う

たとえば自動車で考えると、同じメーカーの軽自動車、SUV、スポーツカーを別々の人が評価し、その点数だけを平均して「このメーカーが1位」と言っているような状態です。

Qwenについて、3回答は汎用モデル、最大性能モデル、コード専用モデルを別々に選んでいました。値段も用途も違うので、同じ表で単純比較できません。

#同じモデル名でも、販売店が違う

AIモデルは、開発会社の公式APIだけでなく、OpenRouterなど別会社の窓口からも使えます。

同じ商品でも、販売店によって次が変わるイメージです。

  • 値段
  • 速度
  • 混雑しやすさ
  • 一度に扱える量
  • データをどこへ送るか
  • 問題が起きた時の保証

そのため、「モデル名」だけでなく「どのProviderから使ったか」を必ず記録します。

#カードが使えるかは、公開ページだけでは分からない

日本のクレジットカードが使えるか、本人確認が必要か、最低いくら入金するかは、実際にアカウントを作らないと分からない場合があります。

AIのWeb調査で「使える」と書いてあっても、実際の契約画面で確認するまでは「条件付き」と考える方が安全です。

#入力できる長さと、出力できる長さは違う

「100万トークン対応」と書かれていても、それは読める量かもしれません。1回で書き出せる量は、もっと少ない場合があります。

長いコード変更を任せるなら、次を分けて確認します。

  • どれだけ読めるか
  • どれだけ書けるか
  • 公式APIの上限
  • OpenRouterなど別Providerの上限

#3つの回答で特に食い違ったこと

主な食い違いは次の通りです。

  • DeepSeekで日本カードが使えるか
  • DeepSeekが1回で出力できる最大量
  • DeepSeekのJSON形式がどこまで厳密か
  • GLMの値段と最大出力
  • Z.ai海外版と中国向けサービスの契約条件
  • Kimiで中国の電話番号やAlipayが必要か
  • Kimiが実際に扱える最大の文脈
  • Cursorで「動く」のか「公式に保証される」のか

これらは導入費用や安全性に直接関係します。都合のよい数字を選んで結論を出すべきではありません。

#1. まず正式な商品名を確認する

  • どこで処理するか
  • 何日保存するか
  • 学習に使うか
  • キャッシュするか
  • 契約書やDPAがあるか
  • 問題が起きた時に連絡が来るか

  • 429やタイムアウトの回数

#推奨する導入手順

#1. 公式情報を固定する

候補ごとに、モデルID、料金、最大出力、リージョン、契約条件、保存・学習・キャッシュ、DPA、ZDR、SLA、廃止予定を確認します。

#2. 第三者APIで横比較する

PoCでは、同じインターフェースと同じテスト課題で比較します。第三者APIは比較の摩擦を減らしますが、安全性や本番適性を自動的に保証するものではありません。

OpenRouterなどは系列横断の初期比較に便利です。一方、候補が少数に絞れ、公式APIが使える場合は、個人開発向け追記・再比較のように公式経路を優先してよいです。本番は常に採用経路で再試験します。

#3. 採用経路で再試験する

上位候補は、公式APIまたは本番で固定するProviderを使って再試験します。速度、上限、Tool Calling、障害率、データ経路が変わる可能性があります。

#4. セキュリティ・法務ゲートを通す

機密コードや顧客情報を扱う場合は、送信禁止情報、マスキング、Provider固定、保存期間、契約文書、越境移転、障害通知を人間が承認します。

#5. 役割別に採用する

1モデルですべてを処理するのではなく、主力、低価格補助、高難度レビュー、フォールバックに分けます。

#この結論を採用する理由

  • 3回答の共通部分を利用できる
  • 矛盾を都合よく解消せず、未確認事項として残せる
  • モデル名が更新されても評価方法を再利用できる
  • 性能だけでなく、契約、運用、セキュリティを判断へ含められる
  • 実際のbuild/test、Tool Calling、費用、人間修正量で比較できる

#採用しなかった考え方

#1. 総合点1位をそのまま採用する

採点対象のモデル世代やProviderが揃っておらず、点数の前提が異なるため採用しません。

#2. 3回答の多数決で事実を決める

複数AIが同じ誤情報を参照する可能性があります。一致は調査優先度を上げますが、一次情報の代わりにはなりません。

#3. 第三者APIを常に最安全とみなす

比較には便利ですが、Routerと実推論ホストの両方を評価する必要があります。自動ルーティングで送信先が変わることもあります。

#4. オープンウェイトなら安全とみなす

自社管理環境で運用すればデータ境界を管理しやすくなりますが、GPU、運用、脆弱性対応、モデル更新、ライセンス確認の負担があります。

#OpenRouterを使うべきか

今回の4系列だけを試すなら、個人開発でも最初は公式APIを推奨します。

  • 最新モデルが最初に利用可能になる
  • Prompt Cacheなどのモデル固有機能を使える
  • Tool Callingの互換性が高い
  • 推論Providerを意識しなくてよい
  • 障害原因を切り分けやすい
  • OpenRouterを経由する追加のデータ経路がない

  • DeepSeek公式で日本カードが通らない
  • APIキーを1つにまとめたい
  • 同じタスクを複数モデルで比較したい
  • 利用上限を一括管理したい
  • Provider障害時に自動切替したい

#結論を一言でいうと

#いま1社・1モデルに決めない

3つのAI調査は、DeepSeek、Qwen、GLMなどを有力候補として挙げました。しかし、値段、契約方法、一度に出力できる量、データの扱いについて、回答が大きく食い違っています。

そのため、今すぐ「このモデルが1位」と決めるのではなく、候補を役割別に残して少額の実験をするのが安全です。

#推奨案

#主力候補

安さとコーディング性能の候補として、DeepSeekの現行高性能モデルを試します。

#日本企業向け候補

日本語、国際契約、リージョン、法人運用を重視し、Qwenの現行国際向けモデルを試します。資料に書かれた名称をそのまま使わず、公式ページで現在のモデルIDを確認します。

#長時間エージェント候補

複数のツールを長く使う仕事では、GLMの現行モデルを比較します。ただし、値段と最大出力の記述が食い違うため、契約前に確認します。

#安い大量処理

分類、前処理、簡単なレビューなどは、DeepSeekの低価格・高速モデルを比較します。

#難しい仕事の比較枠

他モデルが失敗する難しい課題や大きなリポジトリでは、Kimiの現行高性能モデルを限定的に試します。高価になりやすいため、通常の大量処理には使いません。

#進め方

  1. 公式ページで、現在使える正確なモデル名と値段を確認する
  2. OpenRouterなどで同じ課題を試し、候補を絞る。候補が少数で公式APIが使えるなら、最初から公式経路でもよい
  3. 本番で使う公式APIまたは固定Providerでもう一度試す
  4. 顧客情報や非公開コードを送ってよい契約か確認する
  5. 主力、安い補助、難しいレビュー、予備の4役に分ける

#メリット

  • 誤ったランキングで契約する危険を減らせる
  • 実際にかかる費用と人間の手直し時間を比べられる
  • 1つのサービスが止まっても切り替えやすい
  • 安いモデルと高性能モデルを使い分けられる
  • セキュリティや契約条件を説明しやすい

#デメリット

  • 比較試験の準備と記録に手間がかかる
  • 複数のAPIキーや請求を管理する必要がある
  • モデル更新が速く、定期的な再試験が必要になる
  • 機密情報を扱う場合は、法務とセキュリティ確認が増える
  • 最初から1位を決める方法より、決定まで時間がかかる

#経営・営業の判断ポイント

値段の安さだけでなく、次を確認してください。

  • 顧客との契約上、コードやデータを外部AIへ送ってよいか
  • データがどの国で処理・保存されるか
  • 問題発生時の連絡や保証があるか
  • モデルが終了した時に切り替えられるか
  • 人間の修正時間を含めても安いか
  • 日本語の仕様や業務ルールを正しく扱えるか

#最終判断

PoCでは複数モデルを同じ条件で比較し、本番ではモデルID、Provider、データ条件を固定する。
