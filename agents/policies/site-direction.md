# amane AI Lab サイト・編集方針

- Status: Active
- Owner: Koo
- Last Updated: 2026-08-08

この文書は、amane AI Lab を今後どのようなサイトとして育てるか、記事・Benchmark・UIをどの方向へ揃えるかを定める。
技術アーキテクチャの正本は `docs/specs/public-knowledge-base-spec.md` と `docs/adr/` を参照する。

## 1. サイトの位置づけ

amane AI Lab は、一般的なAIニュースブログや製品紹介メディアではない。

**実際のソフトウェア開発を使って、AIエージェントの実装・レビュー・修正・開発手法を試し、その結果と証拠を公開する個人Lab** とする。

狙う認知は、単に「AIに詳しい人」ではなく、次の状態である。

- AI開発を実際に継続している
- 実コード、テスト、CIまで確認している
- モデルの評判ではなく、自分の開発環境で検証している
- 成功結果だけでなく、失敗、制約、見逃しも公開している
- 読者が実務へ持ち帰れる知見を出している

自己評価や宣伝文句で専門性を主張するより、記事、Benchmark、生データ、GitHub一次証拠を見れば活動内容が分かる状態を優先する。

## 2. IN4A・Lab・GitHubの役割分担

公開導線は次の3層で考える。

| 場所 | 主な役割 | 読者に伝えること |
|---|---|---|
| IN4A | 会社、仕事、経歴、実績 | 何を任せられる人物・会社か |
| amane AI Lab | 実験、比較、考察、開発手法 | 今どのAI開発を深く試しているか |
| GitHub | Issue、branch、SHA、PR、CI、コード | 本当にその実験を行ったか |

amane AI Lab をIN4Aの単なる企業ブログにはしない。
Labとして、失敗やモデル差、微妙な結果もそのまま扱える独立性を残す。

## 3. コンテンツの3層構造

### 3.1 Articles

記事は **「何を試し、何が分かったか」** を読みやすく伝える場所とする。

記事本文へ全ログや全候補表を詰め込む必要はない。
入口は読み物として分かりやすくし、詳細データへ移動できる導線を用意する。

基本の流れは次を推奨する。

```text
問い / 実験の理由
↓
先に結果
↓
何を比較したか
↓
なぜ差が出たか
↓
実務でどう使うか
↓
制約・限界
↓
Benchmark / Raw Evidence
```

### 3.2 Benchmarks

`/benchmarks/` はLabの中核コンテンツとして扱う。

ここでは読み物よりも、次の情報を優先する。

- 試行ごとのランキング
- 全候補一覧
- 評価指標とスコア内訳
- 処理時間、Practical Score等の補助指標
- Model + Agent/Harness + Effort
- 実行条件
- branch / Head SHA / tag
- PR
- CI
- finding / verdict
- Raw resultへのリンク
- 機械可読データ（有用な場合）

Benchmarksはヘッダーから常時アクセス可能にし、通常の記事リンクより視覚的に強く扱ってよい。
このサイトが「Lab」であることを最短で伝える導線だからである。

### 3.3 Raw Evidence / GitHub

GitHub上の一次証拠は可能な限り残す。

公開できる範囲で、次を追跡可能にする。

```text
Prompt / Issue
↓
Model + Harness + Effort
↓
branch / Head SHA
↓
PR / diff
↓
CI / test
↓
評価結果
↓
Final synthesis / independent review
```

記事を簡潔にするために、生データ自体を削除してはいけない。
**記事から外すことと、証拠を消すことは別である。**

## 4. ランキング方針

ランキングは興味を引く入口であり、Benchmarkの価値でもあるため、必要以上に隠さない。

試行内で正式な採点結果がある場合は、上位結果を分かりやすく表示してよい。

例:

```text
1位 GPT-5.6 Sol / Codex — 96
2位 GPT-5.6 Terra / Codex — 95
3位 GPT-5.6 Luna / Codex — 94
```

ただし、ランキングの近くに必ず適用範囲を示す。

> この順位は、このIssue・このModel + Agent/Harness + Effort・この1回の試行での結果であり、モデル一般の性能順位ではない。

### 4.1 評価単位

原則として評価単位はモデル名だけではなく、次とする。

```text
Model + Agent/Harness + Effort + execution attempt
```

同一モデルを異なるHarnessで実行した場合は別候補として扱う。

### 4.2 正式スコアが残っていない場合

過去の試行で正式スコアが保存されていない場合、後から記憶や印象で順位を作らない。

その場合は、

- PR
- CI
- Head
- 処理時間
- 保存済みfinding

などの生データを公開し、ランキングは `未記録` とする。

再採点する場合は、元のランキングと混同せず **「再評価ランキング」** と明示し、再評価日と採点基準を残す。

### 4.3 複数ランキング

Coding Qualityと速度は混ぜすぎない。

必要に応じて、

- Coding Score
- Practical Score
- Quality / Time
- Review Score
- Scope Discipline
- Test Quality

などを別軸で示す。

主ランキングが何かを明示し、補助指標だけで総合的な優劣を断定しない。

## 5. 記事の文章方針

文章は、AIが生成した説明文に見えにくい、自然で具体的な日本語を優先する。

### 推奨

- 結果を先に書く
- 実際に起きたことを書く
- 数字、Issue、PR、テストなど具体物を使う
- 一文を必要以上に長くしない
- 「私はこう扱う」のように判断主体を必要に応じて明確にする
- 読者が次に何を確認すればよいか分かるようにする
- 技術用語は必要なものだけ残す

### 避ける

- 抽象語を何段も重ねる
- 「革新的」「圧倒的」「価値を提供する」等の根拠のない宣伝表現
- 何も言っていない一般論で段落を埋める
- 結論より先に長い注意書きを置く
- 同じ意味を言い換えて繰り返す
- 過度な見出し、箇条書き、太字で機械的に整えすぎる

**入口は読みやすく、本文はLabとして証拠に強くする。**

## 6. UI / 情報設計方針

### 6.1 ヘッダー

主導線は原則として次を基準にする。

```text
記事 / Benchmarks / このLabについて / GitHub
```

Benchmarksはサイトの差別化要素なので、通常ナビより目立つCTAとして扱ってよい。
一方、`NEW`、点滅、強い赤・黄、過度な広告表現など、Labの信頼感を損なう強調は避ける。

### 6.2 記事先頭

記事先頭では、次の優先順位を意識する。

1. タイトルが一目で読める
2. 要約が短く読める
3. 重要な結果またはTL;DRへすぐ到達できる
4. タグやメタ情報がタイトルを圧迫しない
5. デスクトップで不要な空白を作らない
6. モバイルでもタイトルと要約が過度に大きくならない

長いタイトルでは、装飾性より可読性を優先する。

## 7. Benchmarkを新しく追加するとき

新しいBenchmarkでは、可能な限り実験開始時点から次を残す。

- benchmark ID / name
- 対象Issueまたは固定課題
- common base / input
- Model
- Agent / Harness
- Effort
- prompt
- executedAt
- branch / Head SHA
- PR
- CI
- 処理時間
- 採点rubric
- 正式score
- ranking
- findings
- raw result
- final synthesisの有無
- independent reviewの有無

**ランキングを公開するなら、ランキングを再現できる証拠も同時に残す。**

過去のFND-01で候補別Coding Scoreがarchiveされなかった点は、今後のBenchmarkでは繰り返さない。

## 8. 信頼性と訂正

Labでは「常に正しかったように見せる」ことより、記録が追えることを優先する。

- 後から問題が判明したら訂正する
- ランキングの採点ミスがあれば更新履歴を残す
- 条件の違いが判明したら注記する
- Final synthesisにも独立レビューを掛けることがある
- CI greenを最終品質判定と同一視しない
- 公開変更は可能な限りGitで巻き戻せる単位にする

失敗や訂正もLabの成果物として扱う。

## 9. 判断に迷ったときの優先順位

サイトや記事の方向性で迷った場合は、次の順で判断する。

1. 読者に誤解を与えないか
2. 実験の証拠を失わないか
3. 結果が分かりやすいか
4. 実務で役立つか
5. Labらしさが伝わるか
6. 見た目が整っているか

見た目を整えるためにランキングや生データを消さない。
逆に、全データを記事本文へ詰め込み、読みづらくする必要もない。

**Articlesで意味を伝え、Benchmarksで結果を見せ、GitHubで証拠を残す。**

これをamane AI Labの基本方針とする。
